P03 Consolidation & Forgetting Pipeline – Implementation Plan
Milestone 0: K0 Kernel Enhancements (Foundation)
Goal: Implement necessary K0 kernel features (Section 4.10) to support P03’s multi-instance and concurrency needs before building the P03 pipeline itself[1]. These enhancements ensure P03 can run with single-writer per space and partitioned execution in a distributed setting.
Epic 0.1: Distributed Advisory Lock Service
•	Issue 0.1.1: Implement AdvisoryLockService in K0 Core. Define a new AdvisoryLockService class in k0/sync/advisory_lock.py providing async methods acquire(lock_key, holder_id, ttl), release(lock_key, holder_id), and heartbeat(lock_key, holder_id)[2][3]. Use a lightweight locking table or Redis (if available) for cross-node coordination.
•	Issue 0.1.2: Lock Key Schema & Single-Writer Guarantee. Use lock key pattern "p03:{tenant_id}:{space_id}" to enforce one consolidation cycle per space at a time[4]. Integrate lock acquire at cycle start and release at cycle end in P03. Ensure a reasonable ttl_seconds (e.g. 5 minutes) and heartbeats during long cycles to avoid premature expiration[5][6].
•	Issue 0.1.3: Error Handling & Fallback. If lock acquisition fails (already held), have P03 abort or retry later. Implement backoff and logging for lock contention. Document limitations (initially single-node if no distributed backend).
•	Issue 0.1.4: Unit Tests for Lock Service. Simulate multiple “nodes” (threads or async tasks) trying to acquire the same lock to verify mutual exclusion. Test normal acquire/release flow and TTL expiration.
Epic 0.2: Partitioned Pipeline Execution Support
•	Issue 0.2.1: Extend PipelineScheduler for Partitioning. Modify k0/scheduler/scheduler.py to accept a partition_key and partition_strategy for scheduled pipelines[7]. Implement PartitionStrategy.SPACE and TENANT options so that consolidation can be scheduled independently per tenant:space[8].
•	Issue 0.2.2: Assign Partition Keys for P03. For P03, set partition_strategy = SPACE and define partition_key as tenant_id:space_id for each trigger[9][10]. Ensure that the scheduler will create separate jobs per space and route them (in a single-node MVP, they queue serially; in multi-node future, different nodes handle different keys).
•	Issue 0.2.3: Scheduler Trigger Adaptation. Update trigger mechanisms (cron, threshold, manual) to incorporate partitioning: e.g., on a global time trigger, scheduler enumerates all active tenant:space combinations and schedules a consolidation job for each. (If necessary, provide a hook to list partitions – e.g., query distinct tenant/space from active data).
•	Issue 0.2.4: Testing Partition Logic. Write tests to simulate multiple spaces: verify that triggers create separate tasks per space and that only one task per space runs at a time. If multi-threading is available, simulate two spaces processing in parallel (for future readiness).
Epic 0.3: Optimistic Concurrency via UnitOfWork
•	Issue 0.3.1: Extend UnitOfWork for Version Checks. Add method execute_with_version_check(sql, params, expected_version_column='version') in k0/uow/unit_of_work.py[11]. This method will append a WHERE {column} = expected_version clause to the SQL UPDATE or perform a check on rows_affected to detect if a write lost a race[12][13]. Return a VersionedWriteResult indicating success or version conflict.
•	Issue 0.3.2: Schema Update for Versioning. Ensure all P03 truth tables have a version or last_updated field to utilize optimistic locking. If not present, add a version INTEGER DEFAULT 0 column to each relevant table (st_epi, st_sem, etc.) as part of the v1→v2 migration (initialized to 0 for existing records).
•	Issue 0.3.3: Integrate Versioned Writes in P03. In P03’s commit phase (R7), use the new execute_with_version_check for each truth record update[14][12]. If a version conflict is detected (which shouldn’t happen in single-writer mode, but could if multiple cycles tried same record), log it and decide to retry or skip the update.
•	Issue 0.3.4: Unit Test Concurrency Handling. Simulate a version conflict: e.g., manually increment a record’s version before P03 writes, and ensure execute_with_version_check returns conflict = True. Verify P03 logic handles it (e.g., retries X times or marks cycle as needing retry).
Epic 0.4: Pipeline Execution Context Extension
•	Issue 0.4.1: Enhance PipelineContext for Node Info. Extend k0/pipelines/context.py (or similar) to include node_id and partition_assignment info[15][16]. node_id can be sourced from an env var or config (unique per instance), and PartitionAssignment can list partitions this node handles in a multi-node setup.
•	Issue 0.4.2: Provide Context to P03. When P03 runs, populate its context with the current node’s ID and the partition it is responsible for (in MVP, single node owns all partitions, but structure for future multi-node is in place). P03 can use this to, for example, skip cycles not assigned to this node (in case scheduler still enqueues globally).
•	Issue 0.4.3: Test Context Usage. Write a small test to ensure that PipelineContext.node_id is accessible within P03 handlers and that partition_assignment reflects expected values (even if just a placeholder in single-node mode). Ensure no stage of P03 assumes global execution when in future it might be partitioned.
•	Issue 0.4.4: Document Interim Limitations. Note that full distributed coordination (multiple node assignment) will be disabled in MVP (feature-flag off) until a cluster management component provides real partition assignments[17][18]. This simply ensures the code is ready for future scaling.
Epic 0.5: Feature Flags for Kernel Features (Interim Mode)
•	Issue 0.5.1: Add Feature Flags for Workarounds. Introduce flags in P03 config to toggle kernel features vs. interim implementation[19]. For example, P03_FF_USE_LOCK_SERVICE (default true). If false, P03 will fall back to a simple CAS lock on a SQLite table row (single-node safe) instead of the new AdvisoryLockService. Similarly, a flag for partitioned_execution to fall back to global execution if needed.
•	Issue 0.5.2: Implement Fallback Lock (Single-Node). As a contingency, implement a simple locking mechanism using an exclusive row in a local st_consolidation_cycles table or an in-memory lock if USE_LOCK_SERVICE is off[19]. This is essentially the workaround noted (e.g., “SQLite table-based CAS”) for single-node deployments.
•	Issue 0.5.3: Ensure Backward Compatibility. Wrap usage of new context fields and scheduler features in conditional checks. The pipeline should still run (albeit without partition isolation) if these kernel enhancements are not present or flags are off. Mark these flags as temporary, with the intention to remove the workarounds once the cluster-aware features are fully deployed[20].
•	Issue 0.5.4: Test Flags On/Off. Verify that when the feature flags are disabled, P03 can still execute end-to-end in a single-node mode (no lock collisions, processes all spaces sequentially). Conversely, with flags on, ensure new code paths (lock service, etc.) are exercised. Adjust default configs such that MVP v2 uses the new features by default (since single developer environment, assume these are implemented and enabled).
Milestone 1: Core Consolidation Pipeline Implementation
Goal: Develop the P03 pipeline’s core logic (MVP v2 features) in a single-node context. This includes the bidirectional reconciliation algorithm, updating all memory layers (R1–R5 logic), forgetting (pruning/R3), and preparing hooks for active learning (contradictions/gaps). The focus is on correctness of consolidation within one tenant:space, using the kernel enhancements as applicable.
Epic 1.1: Consolidation State Machine & Control Flow
•	Issue 1.1.1: Define P03 Pipeline Phases (R0–R8). Establish the pipeline stage structure as per the design. Follow the R0–R8 state machine specified in Appendix G[21], which covers initial event harvest through gap detection. Implement a coordinator (e.g. P03Handlers.reconcile) that will execute these phases in order for a given space’s cycle.
•	R0 (Harvest): gather new input signals/events (e.g., from hippocampal events queue).
•	R1–R5: consolidation algorithms (replay, integrate, semantic reconcile, knowledge update, dream).
•	R6: anchor update (or contradiction resolution stage).
•	R7: final integration/commit of truth updates.
•	R8: gap detection phase.
•	Issue 1.1.2: Implement Cycle Initiation & Finalization. In handle_reconciliation_request (the main entry), implement cycle start logic: mark cycle started (e.g., insert a record in st_consolidation_cycles with cycle_id, timestamps) and acquire the per-space lock (from Epic 0.1) to prevent concurrent cycles[22][4]. On completion, ensure lock release and update cycle record (completed_at, status).
•	Issue 1.1.3: Error Handling & Retry Strategy. Define how errors in a phase affect the cycle. Use the error recovery matrix (Appendix G.4) to decide when to retry, skip, or abort[23]. Implement try/except around each major phase: on non-recoverable error, publish a consolidation.error event with context and safely terminate the cycle (releasing lock)[24]. On recoverable errors, consider retrying the phase or the whole cycle (possibly via the scheduler’s retry_policy configured with backoff[25]).
•	Issue 1.1.4: Event Emission for Cycle Lifecycle. Integrate BusDispatcher to emit pipeline lifecycle events[26]. On start, emit consolidation.cycle.started (with cycle_id, tenant, space, start_time)[26]. On successful completion, emit consolidation.cycle.completed (with cycle_id, status=SUCCESS, counts of decisions, completed_at)[26]. On failure, emit consolidation.error with error details and mark cycle failed. These events will be useful for monitoring and any downstream logic.
•	Issue 1.1.5: Throttling and QoS Compliance. Ensure the cycle adheres to QoS budgets. For instance, if QoSContext tokens or time budget is exhausted mid-cycle, gracefully stop processing further events in this cycle[27]. Use the configured batch.size and max_events_per_cycle from settings[28][29] to limit how much P03 processes per run (e.g., process up to N new events then stop, deferring remaining to next cycle). Test that these limits are enforced.
Epic 1.2: Bidirectional Reconciliation Algorithm (R1–R2 Core)
•	Issue 1.2.1: Query Existing Truth for New Signals. Implement query_truth_for_signal(new_signal, truth_layers) to fetch relevant records from all memory layers[30][31]. Use the parameters specified in the dossier: e.g., query st_epi (episodic) for recent events in same space (limit 10, within last 30 days, perhaps using simhash for approximate matching)[32]. Query st_sem (semantic) for similar pattern types with embedding similarity ≥0.7 (limit 10)[33]. Query other layers: st_proc (procedural) by actor and activity type[34]; st_soc (social) by participants if any[35]; st_kg for any entities present[36]. Collect all retrieved TruthRecord matches.
•	Issue 1.2.2: Integrate Vector Similarity Search (Embedding). Ensure the semantic query leverages vector embeddings via P08. For example, if st_sem or st_vec stores embeddings, use the embedding.search capability to find top-K similar vectors to the new signal’s embedding[37][38]. If P08’s FAISS index is accessible, call it with the new signal’s vector (which should have been generated in P02) to get similar record IDs. Incorporate those into the truth matches list. (If embedding not available, fall back to a simpler text similarity or Jaccard as used in v1 – but since MVP v2 uses UltraBERT, embedding should be present[39].)
•	Issue 1.2.3: Compute Similarities & Determine Best Match. For each truth record retrieved, compute a similarity score to the new signal. Use appropriate metrics: e.g., cosine similarity on embedding vectors for semantic matches, string similarity or simhash distance for episodic text, etc. Use the same threshold values as the design: >0.85 = high similarity, >0.6 moderate, else low[40][41]. Pick the best match (highest similarity) for decision logic[42][40].
•	Issue 1.2.4: Decision Logic Implementation. Implement the reconciliation decision rules exactly as specified[43][44]:
•	If no matches found, decision = CREATE (a genuinely novel pattern)[45][46].
•	If best similarity > 0.85, decision = REINFORCE (strengthen existing truth)[40][47].
•	If 0.6 < best similarity ≤ 0.85, then if the new signal represents a schema change relative to the best match, decision = EVOLVE (version update)[41]; otherwise EXTEND (add new details)[48].
•	If best similarity < 0.6, check for contradiction: if the content of the new signal directly conflicts with the best match (e.g., opposite sentiment), decision = CONTRADICT[44]; else, treat as novel (CREATE)[44][46].
•	Issue 1.2.5: Conflict Detection Helper. Implement is_contradiction(new_signal, truth_record) and analyze_conflict() per design guidelines – e.g., if a truth says “likes X” and new signal says “hates X”, that’s a conflict[49][44]. The conflict analysis can record details (fields that conflict, degree of conflict) for logging or for P06 to consume. Mark the decision with flag_for_p06=True for contradictions[50].
•	Issue 1.2.6: Logging & Audit of Decisions. For each reconciliation decision made, immediately log an audit event via ObservabilityEmitter. Use the schema defined: event_type p03.reconciliation.decision, include cycle_id, tenant_id, space_id, decision_type (REINFORCE/EXTEND/...), source_event_id (the new signal’s ID), target_truth_id (if it matched an existing record), similarity_score, and the confidence_before/after if applicable[51][52]. This will populate st_cognitive_traces or P03’s audit table for later analysis. Ensure this logging is non-blocking (fire-and-forget or on a separate asyncio task) to not slow the pipeline.
Epic 1.3: Applying Memory Updates for Decisions (R2 Implementation)
•	Issue 1.3.1: REINFORCE Action – Strengthen Existing Memory. If decision is REINFORCE, update the target truth record’s fields as specified[40][47]: increment observation_count, boost confidence_score (apply the confidence boosting function with similarity)[47], update last_observed_at timestamp to now, and reset any decay factor to 1.0 (since this recent observation rejuvenates it). Prepare an SQL UPDATE on the corresponding table (episodic or semantic, etc., depending on where the record lives) setting these new values.
•	Issue 1.3.2: EXTEND Action – Add New Details. If decision is EXTEND, gather the new details from the signal that weren’t in the best match (e.g., new location, new attribute)[53][48]. Update the target record: append to JSON fields like source_episodes_json or other attribute lists as appropriate[53], and potentially update confidence if the new detail increases certainty. Implement a helper extract_new_details(signal, record) to identify what to add (for example, if the truth is an activity pattern “Tuesday yoga” and the new signal has a location “CorePower”, add that detail)[54][53]. Perform an SQL UPDATE to save the augmented record.
•	Issue 1.3.3: EVOLVE Action – Schema Evolution. If decision is EVOLVE, create a new record version for the entity/pattern[41]. For example, if the truth was “Prefers Thai food” and new signal indicates “Prefers Vietnamese”, treat this as evolving preference[55]. Mark the old record’s is_canonical flag to 0 (no longer canonical truth)[56] and insert a new record with is_canonical=1 representing the updated truth. Use a helper build_evolved_version(new_signal, old_record) to create the new record data (carry over IDs or link them as previous_version if needed)[57][58]. Ensure both operations (update old, insert new) occur atomically (wrap in one UnitOfWork).
•	Issue 1.3.4: CREATE Action – Insert Novel Truth. If decision is CREATE, determine the target memory layer for insertion[59][46]. Use determine_target_layer(new_signal) – for example, if it’s a frequently occurring event pattern it might go to semantic layer, if it’s a one-off event it stays episodic, etc. (Follow dossier rules or simple logic: perhaps default to episodic for most patterns unless signal explicitly classified as semantic or knowledge type.) Insert a new record into that layer’s table with initial values: confidence score = new_signal.salience_score[59][60], observation_count = 1, last_observed_at = now, is_canonical = 1 by default, etc. Also insert any related info (e.g., if it has associated entities, you might create initial KG links in R4, see below).
•	Issue 1.3.5: Database Write Operations. For each update/insert, utilize the UnitOfWork with optimistic concurrency (from Epic 0.3). For updates, use execute_with_version_check to avoid overwriting a record changed elsewhere[12][13]. For inserts, get the new row ID (or generate a ULID if using deterministic IDs). Handle any constraint errors (e.g., uniqueness conflicts on natural keys) by logging and perhaps converting an intended CREATE into an EXTEND if we find a race condition where another cycle inserted a similar record (though in single-writer mode this shouldn’t happen).
•	Issue 1.3.6: WAL Logging for Persisted Changes. After performing DB writes for decisions, append an entry to the Write-Ahead Log (WAL) for compliance and durability[38][61]. Use storage.wal.append capability to record what changed: e.g., “cycle X updated record Y in st_sem” or the full content of the new/updated record for audit. This ensures that even if the process crashes post-cycle, a durable log of consolidation outcomes exists (helpful for rebuilding indexes or debugging).
•	Issue 1.3.7: Post-Update Hooks (Embedding Index). If a new truth record was created or an existing one significantly changed (especially if it affects its embedding vector), ensure the change is reflected in the vector index. For example, after inserting a new semantic memory, call P08’s API to add the new embedding to FAISS index (if P08 isn’t auto-indexing via triggers). If P08 provides a embedding.encode and embedding.index.add method, invoke those (for MVP, if P02 already stored the vector in st_vec, perhaps emit an event to let P08 know to index it)[37]. Include this step in the transaction if possible or just after, to keep vector store in sync.
Epic 1.4: Synaptic Decay & Forgetting Process (R3)
•	Issue 1.4.1: Implement Decay on Unreinforced Truths. Introduce a routine to run during each cycle (or perhaps periodically as a separate maintenance task) to reduce confidence of truths that haven’t been observed in a while. For each truth record, you could maintain a decay_factor or compute decay based on time since last_observed_at. According to design, if a pattern has not been reinforced for an extended period, its confidence should erode[62]. Apply an exponential decay or linear reduction to the confidence_score. Ensure that when a record is reinforced (Issue 1.3.1), we reset or boost its confidence and maybe set decay_factor back to 1[47].
•	Issue 1.4.2: Identify Candidates for Pruning. Determine the criteria for PRUNE decisions[62]. For MVP, this might be any truth whose confidence falls below a certain threshold (e.g., <0.2) or that hasn’t been observed in > N days. Utilize configured thresholds (perhaps from Appendix F for decay thresholds) to decide which records to archive or delete. Mark these records for removal.
•	Issue 1.4.3: Prune Aged Truth Records. For each record identified above, perform the PRUNE action as specified[62]. Options include: (a) tombstone the record (set a flag or move it to an “archived” state but keep it for history), (b) fully delete the record from the active table, possibly moving it to an archive table. The dossier suggests archiving or tombstoning is acceptable for extended periods of no reinforcement. Implement deletion with care for referential links (e.g., if deleting an episodic memory that’s referenced in semantic layer or KG, handle that).
•	Issue 1.4.4: Cascade Deletion & Cleanup. If a truth record is pruned, ensure related data is cleaned: remove any associated vector from st_vec (embedding store), remove edges in st_kg that pointed to it, etc. For embeddings, use either a direct embedding.index.remove call if available, or mark index for rebuild. According to the erasure handler design, on deletion P03 can request P08 to rebuild the FAISS index[63][64]. For MVP, a simple approach: if any vectors were removed this cycle, emit an event like embedding.index.rebuild for P08 to process.
•	Issue 1.4.5: Integrate Retention Policy (Privacy). Leverage K0’s RetentionEnforcer to also purge data according to privacy bands[65][66]. For instance, if a tenant’s policy says Red-band data lives 30 days, use P03RetentionPolicy to find expired records in memory tables and remove them. Implement P03RetentionPolicy.apply_band_retention(band) to call K0 retention for memory_layer resources[65][66]. This can be done at the end of each cycle for each band, or perhaps triggered on a schedule. Make sure to log how many records were purged per band for audit.
•	Issue 1.4.6: Audit Pruning Decisions. Similar to reconciliation decisions, log each prune action. Use the st_consolidation_audit table with a decision_type like “PRUNE” and include why (e.g., “no observation in 180 days” or “confidence <0.1”)[67][68]. Also emit a consolidation.truth.updated or a specific consolidation.truth.pruned event for external systems if needed to know a truth was removed. Ensure the WAL (from 1.3.6) also records these deletions for compliance.
Epic 1.5: Knowledge Graph Update & Anchoring (R4)
•	Issue 1.5.1: Update Knowledge Graph Entities. When new truths are created or extended, update the Knowledge Graph (KG) to reflect this knowledge. If the new signal or truth has extracted entities (persons, places, etc.), ensure they exist in st_kg_dom (domain entities table) and create or update relationships in st_kg_edges. For example, if an episodic pattern “Alice went to Paris” is consolidated into semantic memory “Alice travels to Paris often”, ensure that the entity “Paris” and “Alice” exist and have a relationship (Alice –[visited]→ Paris) incrementing a count or confidence. Use the P03 logic or helper from dossier algorithms to manage KG updates (Appendix C.5) for R4.
•	Issue 1.5.2: Implement Bayesian Anchor Updates. If the system uses anchors to represent stable user traits or preferences (e.g., an anchor for “Alice’s yoga preference”), update these using a Bayesian approach as described. This likely means treating each reinforcement as evidence towards an anchor’s belief distribution. If feature flag bayesian_anchors is enabled (default true)[69], incorporate the update: e.g., update prior and likelihood to get new posterior confidence for an anchor. This could involve storing counts of behavior contexts in st_anchor_points table and updating them. Ensure this runs for relevant patterns (like preferences, habits).
•	Issue 1.5.3: Handle Anchor Drift & Multi-modal Anchors. Implement logic for anchor drift as per policy[70][71]. If contradictory behaviors for an anchor emerge (e.g., user behaves differently in different contexts), and drift mode is multimodal (default)[72], then instead of forcing one average, allow multiple modes. For example, if anchor “morning routine” has two distinct patterns, maintain two sub-anchors. Use anchor_conflict_threshold (e.g., 0.4 divergence) to decide when to split an anchor into separate modes[70]. If split, update st_anchor_points to reflect two modes and mark them appropriately. Emit an event or log when an anchor is split due to drift (if emit_drift_event is true)[73].
•	Issue 1.5.4: Persist KG and Anchor Changes. Perform SQL INSERT/UPDATE for st_kg_dom, st_kg_edges and st_anchor_points as needed. If new entities are found in a signal, add to st_kg_dom (with type, first seen time, etc.). If new relation discovered or reinforced, upsert into st_kg_edges (with count/confidence). For anchors, if updating counts or splitting, update st_anchor_points records. Use transactions around these changes, and consider foreign keys (if any) between truth tables and KG tables.
•	Issue 1.5.5: Security & Privacy Checks. Ensure that in updating the KG, any privacy constraints (like access control, location privacy) are respected[74]. For instance, if location privacy is enabled, perhaps not store exact coordinates in KG edges or apply anonymization. Also consider encryption for sensitive personal anchors (if K0 Crypto layer supports field encryption)[75] – integrate by marking those fields or using Crypto API to encrypt before store.
•	Issue 1.5.6: Testing KG Updates. Devise tests where a known entity in a new event should cause a KG edge update (e.g., user likes X). After running consolidation, verify the KG tables have the expected entries/updates. Also test anchor drift: simulate conflicting evidence and check that anchor splits into two entries when threshold exceeded, with correct mode counts.
Epic 1.6: Dream Generation Stage (R5, MVP Stub)
•	Issue 1.6.1: Implement R5 Conditional Execution. Add an R5 phase in the state machine that runs after main reconciliation (and possibly after R4) to perform “dream-like” consolidation if conditions allow. Check the r5_execution_mode policy[76]: if set to disabled (the MVP default recommendation), skip this phase entirely. If conditional (default in config)[76], only run R5 when the system is not under heavy load. This means check the backlog of pending signals and current time: e.g., only run if fewer than r5_backlog_threshold events pending and if we have at least r5_min_idle_seconds of expected idle time[77]. These values (e.g., backlog_threshold 500, idle 60s) should be read from config[77].
•	Issue 1.6.2: Dream Logic (TDL-HCO Stub). If R5 runs, implement a simplified “dream” algorithm for MVP. Since full CPN/TPN-MCTS is deferred, use a placeholder approach: for example, randomly pick some existing memories (truths) and slightly perturb or combine them to simulate a new hypothetical signal (this could mimic the Temporal Difference Learning – Hippocampal-Cortical Oscillation idea mentioned). The goal is to introduce some creative noise to potentially discover new connections. Mark these generated signals as system-generated and perhaps enqueue them into the consolidation process (as new HippEvents) for the next cycle. Note: This logic is intentionally minimal in MVP; clearly comment that a more advanced algorithm will replace it in Phase 2[78][79].
•	Issue 1.6.3: Integration of Dream Outputs. If any dream signals are generated, decide how to handle them. One approach: directly insert them into episodic memory (st_epi) with a flag indicating they are synthetic, so they’ll be considered in future consolidation cycles as if they were “replayed experiences”. Alternatively, queue them to P03’s input (perhaps via the same hipp.committed event pathway or a special topic) to be processed next. Implement whichever is simpler for MVP (e.g., just treat them as new HippEvents and call P03Handlers.reconcile recursively or schedule a new cycle).
•	Issue 1.6.4: Safeguards and Flags. Ensure that if enhanced_dream_exploration feature flag is off (it will be off for MVP)[78], the dream stage either does nothing or runs only the basic stub. If on, it might indicate a future phase with heavier logic – but since MVP is focusing on basic, we keep it off by default. Include a developer note or TODO in code referencing that full R5 implementation (with GPU support etc.) is expected in v2.5+ and is not covered in this plan[80].
•	Issue 1.6.5: Testing R5 behavior. With dream disabled (the default), verify that the pipeline completes without entering R5. With it enabled (set flags to always run R5), test that a simple synthetic event is generated and inserted appropriately. Also test the skip conditions: artificially inflate a backlog or set a flag to simulate “system busy” and verify R5 correctly skips when it should (and perhaps logs a message that it skipped due to load).
Epic 1.7: Active Learning Hooks (Contradictions & Gaps, R6 & R8)
•	Issue 1.7.1: Handle Contradiction Outcomes. When a CONTRADICT decision is returned in reconciliation (from Issue 1.2.4), implement the handling: do not integrate the conflicting signal into the truth immediately. Instead, mark the involved truth record as having a pending contradiction. This could involve setting a status = PENDING_CONTRADICTION or similar on that record, or storing the conflict in a separate table. Reduce the confidence of the truth slightly (apply contradict_confidence_penalty, default 0.3) to reflect uncertainty[81][82]. Crucially, we flag for P06 Active Learning to resolve it[49][44].
•	Issue 1.7.2: Enqueue Contradiction for P06. Use the K0 Bus or Outbox to notify P06 of the contradiction. The dossier suggests an escalation topic: publish an event p06.contradiction.escalate.v1 containing details of the conflict[82][83] (e.g., the IDs of the two conflicting truths or signals, the conflicting facts). Alternatively, push a task into a st_learning_queue for P06. In MVP, implement whichever mechanism P06 expects: likely via the event bus since escalation_topic is provided in config[83]. Ensure to include a unique identifier for this contradiction case and perhaps a reference back to the original P03 cycle or truth IDs.
•	Issue 1.7.3: Limit Contradiction Backlog. Before enqueuing new contradictions, check how many are unresolved. Use contradict_max_pending (default 50) from config[82]. If the number of pending contradiction cases for this tenant/space exceeds that, we might decide not to flag additional ones (or to coalesce them) to avoid overloading P06. Implement this policy: if pending_count >= max_pending, simply log and skip raising new P06 tasks until some are resolved, or consider marking cycle as complete with a warning.
•	Issue 1.7.4: Implement Gap Detection (Knowledge Gaps). After consolidation (post R7 commit), run a Gap Detection phase (R8). This scans the current truth state for areas of low confidence or missing coverage. For example, if certain entity has very few observations or an anchor’s confidence is low relative to its importance, that could be a knowledge gap. Another example: if an expected pattern (based on global trends) is not present in this user’s data, that might be a gap to explore. Implement a strategy as per the design or simplified: e.g., iterate over key anchors or categories and find those with confidence below a threshold or high entropy. Mark those as gaps.
•	Issue 1.7.5: Enqueue Gap for Active Learning. For each identified gap, create a task for P06. Likely this would be an entry in st_learning_queue specifying the type of gap and context (for example: “User has low-confidence knowledge about X, consider asking a question or scheduling a probing event”). Use storage.outbox.enqueue or direct DB insertion to add to the queue[38]. Include a priority score for the gap (perhaps the entropy or potential information gain). Adhere to config: do not overfill the queue. Specifically, if the st_learning_queue length exceeds gap_queue_max_depth (500 by default) skip adding new gaps[84][85].
