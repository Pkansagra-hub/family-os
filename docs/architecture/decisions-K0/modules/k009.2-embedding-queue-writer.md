# k009.2 - Embedding Queue Writer (Job Scheduling for Vector Generation)

**Status**: ACCEPTED | **Parent**: [k009 - Pipeline Builders Architecture](k009-pipeline-builders.md)

---

## Executive Summary

**M14 (Embedding Queue Writer)** enqueues embedding generation jobs to `st_embedding_queue` for P08 background processing, decoupling fast memory writes (P02) from slow vector computation (P08).

**Key Design Points**:
1. **Job Creation**: Insert PENDING row with embedding_id from M02 CA1
2. **Deferred Computation**: P08 picks up jobs asynchronously
3. **Status Lifecycle**: PENDING → IN_PROGRESS → READY → (optional FAILED)
4. **Idempotency**: Duplicate embedding_id triggers SKIP (no-op)
5. **Fast Write**: <5ms P95 (single row insert)

**Performance Budget**: <5ms P95 (single INSERT, indexed PK)

---

## Context

### Vector Generation Deferral Problem

Embedding generation is **expensive** (50-200ms per event):
- Text → 384-dimensional vector (sentence-transformers model)
- GPU inference or batch processing
- Too slow for P02 write path (<100ms budget)

**Solution**: Defer to P08 background pipeline:
- P02: Fast write (enqueue job)
- P08: Slow vector computation (batch processing)

### st_embedding_queue Schema

```sql
CREATE TABLE st_embedding_queue (
  embedding_id TEXT PRIMARY KEY,      -- UUID from M02 CA1
  event_id TEXT NOT NULL,             -- FK to st_hipp_events.event_id
  wal_pos INTEGER NOT NULL,           -- FK to st_wal.wal_pos
  status TEXT NOT NULL DEFAULT 'PENDING',  -- PENDING | IN_PROGRESS | READY | FAILED
  attempt_count INTEGER DEFAULT 0,    -- Retry counter
  created_at INTEGER NOT NULL,        -- Unix timestamp when queued
  updated_at INTEGER NOT NULL,        -- Last status update
  claimed_at INTEGER,                 -- When worker claimed job (IN_PROGRESS)
  completed_at INTEGER,               -- When vector ready (READY)
  error_message TEXT,                 -- Failure reason (if FAILED)

  FOREIGN KEY (event_id) REFERENCES st_hipp_events(event_id),
  FOREIGN KEY (wal_pos) REFERENCES st_wal(wal_pos)
);

CREATE INDEX idx_embedding_queue_status ON st_embedding_queue(status);
CREATE INDEX idx_embedding_queue_created ON st_embedding_queue(created_at);
```

### Status Lifecycle

```
PENDING → IN_PROGRESS → READY
           ↓
         FAILED (after max retries)
```

**Transitions**:
1. **P02 writes**: Status = PENDING, attempt_count = 0
2. **P08 claims**: Status = IN_PROGRESS, claimed_at = now()
3. **P08 completes**: Status = READY, completed_at = now()
4. **P08 fails**: Status = FAILED, error_message set (after max retries)

### Idempotency

**Duplicate embedding_id handling**:
- P02 uses `INSERT OR IGNORE` (SQLite) or `INSERT ON CONFLICT DO NOTHING` (Postgres)
- If embedding_id exists → skip (no error, no overwrite)
- Prevents duplicate jobs on P02 retries

## Decision

### Algorithm

```python
async def enqueue_embedding_job(
    embedding_id: str,
    event_id: str,
    wal_pos: int,
    db: Database
) -> bool:
    \"\"\"
    Enqueue embedding generation job for P08.

    Performance: <5ms P95 (single INSERT)
    Returns: True if inserted, False if duplicate (idempotent skip)
    \"\"\"
    now = int(time.time())

    try:
        await db.execute(
            \"\"\"
            INSERT INTO st_embedding_queue (
                embedding_id, event_id, wal_pos, status,
                attempt_count, created_at, updated_at
            ) VALUES (?, ?, ?, 'PENDING', 0, ?, ?)
            ON CONFLICT (embedding_id) DO NOTHING
            \"\"\",
            (embedding_id, event_id, wal_pos, now, now)
        )
        return True  # Inserted
    except IntegrityError:
        # Duplicate embedding_id (should not happen with ON CONFLICT)
        return False  # Skipped
```

### P08 Worker Claim Pattern

```python
async def claim_embedding_job(db: Database) -> Optional[EmbeddingJob]:
    \"\"\"
    P08 worker claims next PENDING job.

    Uses SELECT FOR UPDATE to avoid race conditions.
    \"\"\"
    async with db.transaction() as tx:
        job = await tx.execute(
            \"\"\"
            SELECT embedding_id, event_id, wal_pos
            FROM st_embedding_queue
            WHERE status = 'PENDING'
            ORDER BY created_at ASC
            LIMIT 1
            FOR UPDATE SKIP LOCKED
            \"\"\"
        ).fetchone()

        if not job:
            return None

        await tx.execute(
            \"\"\"
            UPDATE st_embedding_queue
            SET status = 'IN_PROGRESS',
                claimed_at = ?,
                updated_at = ?,
                attempt_count = attempt_count + 1
            WHERE embedding_id = ?
            \"\"\",
            (int(time.time()), int(time.time()), job[\"embedding_id\"])
        )

        await tx.commit()
        return job
```

### P08 Completion

```python
async def mark_embedding_ready(
    embedding_id: str,
    db: Database
):
    \"\"\"
    P08 marks job complete after vector stored.
    \"\"\"
    await db.execute(
        \"\"\"
        UPDATE st_embedding_queue
        SET status = 'READY',
            completed_at = ?,
            updated_at = ?
        WHERE embedding_id = ?
        \"\"\",
        (int(time.time()), int(time.time()), embedding_id)
    )
```

## Alternatives Considered

### Alternative 1: Inline Embedding Generation (Rejected)

**Approach**: Compute vector in P02 write path.

**Pros**: No queue management

**Cons**:
- ❌ Latency: 50-200ms per event (exceeds P02 budget)
- ❌ Blocking: P02 waits for GPU inference
- ❌ Scalability: GPU bottleneck affects write throughput

**Rejected**: Too slow for P02 write path.

### Alternative 2: External Queue (Redis, RabbitMQ) (Rejected)

**Approach**: Use external message queue instead of DB table.

**Pros**: Mature queue semantics (retry, DLQ)

**Cons**:
- ❌ Complexity: New infrastructure dependency
- ❌ Consistency: Queue state separate from DB state
- ❌ Debugging: Harder to query job status

**Rejected**: DB-backed queue is simpler (same transaction guarantees).

### Alternative 3: Trigger-Based Enqueue (Rejected)

**Approach**: Database trigger on st_hipp_events INSERT → auto-enqueue.

**Pros**: No explicit module

**Cons**:
- ❌ Hidden logic: Triggers hard to debug
- ❌ No retry control: Cannot customize failure policy
- ❌ Tight coupling: st_hipp_events knows about embeddings

**Rejected**: Explicit module is clearer.

### Alternative 4: Chosen - DB-Backed Queue

**Pros**:
- ✅ Simple: Single INSERT operation
- ✅ Consistent: Same transaction as st_hipp_events write
- ✅ Queryable: SQL queries for monitoring
- ✅ Idempotent: ON CONFLICT DO NOTHING

**Cons**:
- ⚠️ Polling: P08 must poll for new jobs (no push notification)
- ⚠️ Table growth: Completed jobs need periodic cleanup

**Why Chosen**: Simplest approach that meets requirements.

## Consequences

### Positive

✅ **Fast P02 Write**: <5ms P95 (defers slow vector computation)
✅ **Decoupled Pipelines**: P02 independent of P08 performance
✅ **Queryable Status**: SQL queries for job monitoring
✅ **Retry Support**: attempt_count enables P08 retry logic

### Negative (with Mitigations)

⚠️ **Polling Overhead**: P08 must poll for PENDING jobs
- **Mitigation**: Batch polling (fetch 10-100 jobs at once)
- **Monitoring**: Track queue depth (alert if >1000 pending)

⚠️ **Table Growth**: Completed jobs accumulate
- **Mitigation**: Periodic cleanup (DELETE WHERE status='READY' AND completed_at < 7 days ago)
- **Alternative**: Archive to separate table for long-term metrics

⚠️ **No Priority Queue**: FIFO ordering only
- **Mitigation**: Add priority column (future enhancement)
- **Current**: Order by created_at (sufficient for P02)

### Performance

| Operation | P50 | P95 | P99 |
|-----------|-----|-----|-----|
| INSERT (P02) | 1.0ms | 3.0ms | 5.0ms |
| Claim (P08) | 2.0ms | 5.0ms | 8.0ms |
| Update status | 0.5ms | 1.0ms | 2.0ms |
| **Total P02** | **1.0ms** | **3.0ms** | **5.0ms** |

**Queue depth target**: <100 PENDING jobs (indicates P08 keeping up)

## Testing Strategy

```python
def test_enqueue_job():
    success = await enqueue_embedding_job(
        embedding_id=\"emb_abc123\",
        event_id=\"evt_xyz789\",
        wal_pos=42,
        db=db
    )
    assert success == True

    # Verify row created
    job = await db.execute(
        \"SELECT * FROM st_embedding_queue WHERE embedding_id = 'emb_abc123'\"
    ).fetchone()
    assert job[\"status\"] == \"PENDING\"
    assert job[\"attempt_count\"] == 0

def test_idempotent_enqueue():
    # First insert succeeds
    await enqueue_embedding_job(\"emb_abc123\", \"evt_xyz789\", 42, db)

    # Second insert skipped (duplicate)
    success = await enqueue_embedding_job(\"emb_abc123\", \"evt_xyz789\", 42, db)
    assert success == False  # Skipped

def test_p08_claim():
    # Enqueue job
    await enqueue_embedding_job(\"emb_abc123\", \"evt_xyz789\", 42, db)

    # P08 claims job
    job = await claim_embedding_job(db)
    assert job[\"embedding_id\"] == \"emb_abc123\"

    # Verify status updated
    status = await db.execute(
        \"SELECT status FROM st_embedding_queue WHERE embedding_id = 'emb_abc123'\"
    ).fetchone()
    assert status[\"status\"] == \"IN_PROGRESS\"
```

## Monitoring

**Key Metrics**:
- **Queue depth**: COUNT(*) WHERE status='PENDING'
- **Age of oldest job**: MIN(created_at) WHERE status='PENDING'
- **Success rate**: COUNT(*) WHERE status='READY' / total jobs
- **Failure rate**: COUNT(*) WHERE status='FAILED' / total jobs

**Alerts**:
- Queue depth >1000 (P08 falling behind)
- Oldest job >1 hour (processing stuck)
- Failure rate >5% (model issues)

## Exception to Builder Pattern (IMPORTANT)

### M14 as Direct Writer

**ADR k009 (parent)** establishes the **builder pattern** for P02:
- **Builders** (M13, M14) construct data structures (row dicts, job dicts)
- **Writers** (M16, M17) execute database writes and event emissions

**M14 Exception**: Unlike M13 (which builds row → M16 writes), **M14 writes directly to st_embedding_queue**.

**Evidence from Contract** (`k0/contracts/modules/builders.embedding_queue_write.v1.yaml`):
```yaml
side_effects:
  - write:st_embedding_queue
```

**Rationale for Exception**:

1. **Operational Isolation**: Embedding generation is deferred work (P08 pipeline), not core memory ACID boundary
   - M14 failure should NOT block M16 memory commit
   - Embedding queue is operational queue, not critical memory data

2. **Transaction Independence**: M14 and M16 run in separate transactions
   - M14 writes st_embedding_queue (single table, idempotent ON CONFLICT DO NOTHING)
   - M16 writes st_hipp_events + st_pipeline_processed (2-table atomic transaction)
   - Both can succeed/fail independently

3. **Retry Flexibility**: M14 can retry independently without affecting M16
   - P08 handles missing embedding jobs gracefully
   - Orphaned embedding jobs (M14 succeeded, M16 failed) are rare and acceptable

**Contrast with M13**:
- **M13** (hipp_events_row builder): Pure builder (no side effects)
  - Constructs row dict from all enrichment outputs
  - M16 writes the row atomically with pipeline tracking
- **M14** (embedding_queue_write): Hybrid builder-writer (has side effects)
  - Constructs job dict from M02 embedding_id
  - **Also writes to st_embedding_queue directly** (exception to pattern)

**Architectural Principle**: Builder pattern primarily governs **hippocampal row construction**, not every side-table write. Specialized operational queues (like st_embedding_queue) may have dedicated writers for isolation and flexibility.
