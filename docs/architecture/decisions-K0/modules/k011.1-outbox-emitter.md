# k011.1 - Outbox Event Emitter (P02 Downstream Propagation)

**Status**: ACCEPTED | **Parent**: [k011 - Core Event Emission Architecture](k011-core-emitters.md)

---

## Executive Summary

**M17 (Outbox Event Emitter)** propagates P02 completion to downstream pipelines via **6 exit topics**, using the **outbox pattern** for transactional event emission.

**Key Design Points**:
1. **6 Exit Topics**: Emit to P03, P04, P06, P07, P08, and observability systems
2. **Outbox Pattern**: Write events to st_outbox (not direct NATS publish)
3. **Transactional Guarantee**: Events part of M16 UnitOfWork (atomicity with storage)
4. **Relay Worker Separation**: BusDispatcher workers poll st_outbox and publish to NATS
5. **Performance Target**: <10ms P95 for 6-event batch INSERT

**Eventual Consistency**: Events published **after** M16 commit (milliseconds delay via relay workers).

## Context

### P02 Exit Architecture

**Pipeline Flow**:
```
M16 (Atomic Write) → M17 (Emit Events) → BusDispatcher Relay → NATS Topics → Downstream Pipelines
                      ↑
                THIS ADR
```

**M17 Responsibilities**:
- **Input**: Confirmation from M16 (storage committed)
- **Output**: 6 events written to st_outbox

### Outbox Pattern vs. Direct Publish

**Why NOT Direct NATS Publish?**

**Problem with direct publish**:
```python
# ❌ BAD: Direct publish (no transactional guarantee)
await context.uow.hipp_events.insert(row)
await nats_client.publish("workspace.wm.updated.v1", payload)  # NOT atomic!
await context.uow.commit()

# If commit fails → event already published (orphaned)
# If publish fails → commit succeeds but no event (lost notification)
```

**Outbox Pattern Solution**:
```python
# ✅ GOOD: Outbox pattern (transactional guarantee)
async with context.uow.begin():
    await context.uow.hipp_events.insert(row)
    await context.uow.outbox.insert({
        "topic": "workspace.wm.updated.v1",
        "payload": payload,
        "status": "PENDING"
    })
    await context.uow.commit()  # Atomically commits BOTH

# BusDispatcher relay worker (separate process):
while True:
    batch = await poll_outbox(status="PENDING", limit=128)
    for msg in batch:
        await nats_client.publish(msg.topic, msg.payload)
        await update_outbox(msg.id, status="SENT")
```

**Transactional Guarantee**:
- M16 commits st_hipp_events + st_outbox together (same transaction)
- If M16 fails → no outbox entries (consistent)
- If M16 succeeds → outbox entries guaranteed (relay worker publishes later)

### BusDispatcher Relay Workers

**Architecture**:
```
st_outbox (database table)
   ↓ poll every 100ms
BusDispatcher Relay Worker (k0/bus/relay.py)
   ↓ NATS publish
NATS JetStream (message broker)
   ↓ subscribe
Downstream Pipelines (P03, P04, P06, P07, P08)
```

**Relay Worker Responsibilities**:
1. Poll st_outbox WHERE status='PENDING' (batch 128)
2. Publish each message to NATS topic
3. Update st_outbox status='SENT' (or 'FAILED' after 3 retries)
4. Handle backpressure (slow consumers block relay, not P02)

**Relay Worker Config**:
```yaml
# k0/config/bus_relay.yaml
polling_interval_ms: 100
batch_size: 128
max_retries: 3
retry_backoff_ms: 500
nats_url: "nats://localhost:4222"
```

**Failure Modes**:
- **NATS unavailable**: Relay worker retries (outbox entries stay PENDING)
- **Slow consumers**: Backpressure (st_outbox grows, relay worker blocks)
- **Poison messages**: After 3 retries → status='FAILED', alert ops

### Performance Requirements

**Latency Budget**: <10ms P95 (6-event batch INSERT to st_outbox)
- Per-event INSERT: ~1.5ms (10 columns, 2 indexes)
- 6 events × 1.5ms = 9ms
- Buffer: 1ms (connection pool overhead)

**Relay Worker Latency**: 100-300ms (eventual consistency)
- Poll interval: 100ms
- NATS publish: 1-5ms per message
- Update status: 1ms per message
- Total: 100ms (polling delay) + 6×6ms (publish+update) = ~136ms

**End-to-End Latency** (P02 commit → downstream pipeline receives event):
- M16 commit: 30ms
- M17 outbox write: 10ms
- Relay worker polling delay: 0-100ms (average 50ms)
- NATS publish + propagation: 5ms
- **Total: 95ms P50, 145ms P95**

### Idempotency & Deduplication

**Outbox Idempotency**:
- **cognitive_trace_id** links events to source WAL entry
- **Deduplication key**: (cognitive_trace_id, topic)
- **INSERT ON CONFLICT DO NOTHING**: Skip duplicate outbox writes

```python
# Idempotent outbox write
await context.uow.outbox.insert_or_skip({
    "cognitive_trace_id": "ct_abc123",
    "topic": "workspace.wm.updated.v1",
    "payload": payload
})
# If already exists (e.g., M17 retry) → no-op, return existing row
```

**Downstream Consumer Idempotency**:
- **event_id** is globally unique (never reused)
- Downstream pipelines deduplicate by event_id
- Safe for at-least-once NATS delivery

## Decision

### Outbox Pattern with Transactional Emission

**Architecture**: Write events to st_outbox as part of M16 UnitOfWork, relay workers poll and publish to NATS.

**Implementation Pattern**:

```python
# k0/modules/core/event_emitter.py

async def run(message: Message, context: ModuleContext, **config) -> dict:
    """
    M17: Outbox Event Emitter

    Emits 6 downstream events after M16 storage commit:
    1. workspace.wm.updated.v1 (P04 working memory)
    2. core.affect.analyzed.v1 (P06 learning)
    3. space.resolution.complete.v1 (P07 access control)
    4. embedding.enqueue.v1 (P08 vector generation)
    5. p02.hippocampus.pattern_separated.v1 (P03 consolidation)
    6. p02.write.complete.v1 (observability)

    Returns:
        dict: {
            "event_id": str,
            "events_emitted": int,
            "outbox_ids": list[int]
        }
    """
    # Extract data from M16 output + enriched context
    event_id = message.get("event_id")
    wal_pos = message.get("wal_pos")
    cognitive_trace_id = message.get("cognitive_trace_id")

    # Retrieve enriched data from context (set by M01-M12)
    enriched = context.get("enriched_data", {})

    # Build 6 event payloads
    events = [
        # 1. Working Memory update
        {
            "topic": "workspace.wm.updated.v1",
            "payload": {
                "event_id": event_id,
                "space_id": enriched["space_id"],
                "salience_score": enriched["salience_score"],
                "affect_band": enriched["affect_band"],
                "social_context": enriched["social_context"],
                "event_time_utc": enriched["event_time_utc"],
                "actor_id": enriched["actor_id"]
            }
        },

        # 2. Affect analysis (for learning)
        {
            "topic": "core.affect.analyzed.v1",
            "payload": {
                "event_id": event_id,
                "affect_valence": enriched["affect_valence"],
                "affect_arousal": enriched["affect_arousal"],
                "affect_band": enriched["affect_band"],
                "dominant_emotions": enriched["dominant_emotions"],
                "model_version": enriched["affect_model_version"]
            }
        },

        # 3. Space resolution (for ACL sync)
        {
            "topic": "space.resolution.complete.v1",
            "payload": {
                "event_id": event_id,
                "space_id": enriched["space_id"],
                "owner_id": enriched["owner_id"],
                "co_owners": enriched["co_owners"],
                "visible_to": enriched["visible_to"],
                "author_role": enriched["author_role"]
            }
        },

        # 4. Embedding job (for P08)
        {
            "topic": "embedding.enqueue.v1",
            "payload": {
                "embedding_id": enriched["embedding_id"],
                "event_id": event_id,
                "vector_kind": "episodic_memory",
                "model_id": "text-embedding-3-small",
                "text": enriched["text"],
                "priority": "NORMAL",
                "status": "PENDING"
            }
        },

        # 5. DG fingerprints (for P03 consolidation)
        {
            "topic": "p02.hippocampus.pattern_separated.v1",
            "payload": {
                "event_id": event_id,
                "simhash_hex": enriched["simhash_hex"],
                "minhash32": enriched["minhash32"],
                "text_normalized": enriched["text_normalized"],
                "wal_pos": wal_pos
            }
        },

        # 6. Telemetry (for observability)
        {
            "topic": "p02.write.complete.v1",
            "payload": {
                "event_id": event_id,
                "wal_pos": wal_pos,
                "latency_ms": context.elapsed_ms(),
                "module_timings": context.get_module_timings(),
                "idempotency_skipped": message.get("idempotency_skipped", False)
            }
        }
    ]

    # Write all 6 events to st_outbox (part of M16 UnitOfWork or separate)
    outbox_ids = []
    async with context.uow.begin() as txn:
        for event in events:
            outbox_id = await txn.outbox.insert_or_skip({
                "cognitive_trace_id": cognitive_trace_id,
                "topic": event["topic"],
                "payload": json.dumps(event["payload"]),
                "status": "PENDING",
                "created_at": context.now()
            })
            outbox_ids.append(outbox_id)

        await txn.commit()

    context.log.info(
        "P02 events emitted to outbox",
        event_id=event_id,
        topics=[e["topic"] for e in events],
        outbox_ids=outbox_ids
    )

    return {
        "event_id": event_id,
        "events_emitted": len(events),
        "outbox_ids": outbox_ids
    }
```

**Transactional Integration with M16**:

**Option A: Separate UnitOfWork** (chosen):
- M16 commits st_hipp_events/st_embedding_queue/st_pipeline_processed
- M17 opens **new UnitOfWork** for st_outbox writes
- **Trade-off**: 2 transactions (~40ms total), but cleaner separation

**Option B: Extend M16 UnitOfWork**:
- M16 includes st_outbox writes in same transaction
- M17 just builds payloads (no database writes)
- **Trade-off**: 1 transaction (~35ms), but M16 bloated with emission logic

**Chosen: Option A (separate transactions)** for modularity (M16/M17 decoupled).

**BusDispatcher Relay Worker**:

```python
# k0/bus/relay.py

async def relay_outbox_to_nats(config: RelayConfig):
    """
    Poll st_outbox and publish PENDING messages to NATS.

    Runs as background worker (separate from P02).
    """
    nats_client = await connect_nats(config.nats_url)

    while True:
        # Poll st_outbox for PENDING messages
        async with uow.begin() as txn:
            batch = await txn.outbox.poll_pending(
                limit=config.batch_size,
                max_age_seconds=config.max_age_seconds
            )

        for msg in batch:
            try:
                # Publish to NATS topic
                await nats_client.publish(
                    subject=msg.topic,
                    data=msg.payload.encode('utf-8'),
                    headers={"cognitive_trace_id": msg.cognitive_trace_id}
                )

                # Mark as SENT
                async with uow.begin() as txn:
                    await txn.outbox.update_status(
                        msg.id,
                        status="SENT",
                        sent_at=datetime.utcnow()
                    )
                    await txn.commit()

            except NatsError as e:
                # Retry with backoff
                await handle_publish_failure(msg, e, config)

        # Sleep before next poll
        await asyncio.sleep(config.polling_interval_ms / 1000)
```

## Alternatives Considered

### Alternative 1: Direct NATS Publish (No Outbox)

**Approach**: M17 publishes directly to NATS topics (no st_outbox intermediary)

**Pros**:
- Lower latency (no polling delay, 5ms vs. 100ms)
- Simpler architecture (no relay workers)
- Fewer database writes (6 events/sec → 0 writes)

**Cons**:
- ❌ **No transactional guarantee**: M16 commit ≠ event emission
- ❌ **Lost events on failure**: NATS unavailable → event never sent
- ❌ **No retry logic**: Publish fails → orphaned downstream state
- ❌ **Debugging nightmare**: No record of emitted events (can't replay)

**Rejected**: Transactional guarantee **critical** for P02 correctness (event stored → event published).

### Alternative 2: Two-Phase Commit (2PC)

**Approach**: Distributed transaction across PostgreSQL (st_hipp_events) and NATS (event publish)

**Pros**:
- Strongest atomicity guarantee (both succeed or both fail)
- No eventual consistency delay

**Cons**:
- ❌ **50-100ms latency**: 2× network round trips
- ❌ **NATS doesn't support XA**: Would need custom 2PC coordinator
- ❌ **Blocking**: Coordinator failure blocks all participants
- ❌ **Overkill**: PostgreSQL ACID + outbox pattern sufficient

**Rejected**: Complexity not justified (outbox pattern achieves 99.9% atomicity with simpler design).

### Alternative 3: Event Sourcing (All State from Events)

**Approach**: Store events in event log, rebuild st_hipp_events from events on query

**Pros**:
- Perfect audit trail (every state change recorded)
- Time travel (replay events to any point)
- Natural event emission (no separate st_outbox)

**Cons**:
- ❌ **Query complexity**: Rebuild projections on every read (slow)
- ❌ **Storage overhead**: Event log grows unbounded (cannot delete)
- ❌ **Architectural shift**: Requires rewrite of entire storage layer
- ❌ **Learning curve**: Team unfamiliar with event sourcing patterns

**Rejected**: Too large a pivot for P02 requirements (outbox pattern sufficient for event emission).

### Alternative 4: Kafka Outbox Connector

**Approach**: Use Debezium or similar CDC tool to stream st_outbox changes to Kafka/NATS

**Pros**:
- No custom relay workers (Debezium handles polling + publish)
- Industry-standard tool (battle-tested)
- Automatic retry and dead-letter queue

**Cons**:
- ❌ **External dependency**: Requires Kafka/Debezium deployment
- ❌ **Operational overhead**: Another system to monitor/debug
- ❌ **Latency**: CDC typically 100-500ms (similar to custom relay)
- ❌ **Overkill for 100 events/sec**: Kafka better for 10K+ events/sec

**Rejected**: Custom relay worker simpler for P02 throughput (100-200 events/sec).

## Consequences

### Positive

✅ **Transactional Event Emission**
- M16 commit + st_outbox writes atomic (same UnitOfWork or back-to-back)
- If M16 fails → no outbox entries (consistent state)
- If M16 succeeds → outbox entries guaranteed (relay worker publishes later)

✅ **Guaranteed Delivery**
- Relay worker retries failed publishes (max 3 attempts)
- Poison messages marked FAILED (alert ops)
- Event never lost (stored in st_outbox until published)

✅ **Downstream Decoupling**
- P02 never blocks on downstream consumer speed (relay worker buffers)
- P04/P06/P07/P08 can fail independently (NATS redelivery)
- st_outbox acts as durable queue (survives NATS outages)

✅ **Observability**
- st_outbox table shows pending/sent/failed counts
- Relay worker metrics: publish_latency_ms, retry_count, backlog_size
- Debugging: Query st_outbox by cognitive_trace_id to see emitted events

✅ **Idempotency**
- INSERT ON CONFLICT DO NOTHING (cognitive_trace_id, topic)
- Duplicate M17 executions → no duplicate outbox entries
- Downstream consumers deduplicate by event_id

### Negative

⚠️ **Eventual Consistency (100ms delay)**
- Events published **after** M16 commit (relay worker polling interval)
- P04 sees new working memory entry 100ms after P02 commit
- **Mitigation**: Acceptable for background processing (P02 not user-facing)

⚠️ **Relay Worker Single Point of Failure**
- If relay worker crashes → outbox entries stay PENDING (events not published)
- Downstream pipelines stalled until relay worker restarts
- **Mitigation**: Deploy relay worker with k8s Deployment (auto-restart), multi-replica for HA

⚠️ **st_outbox Growth (Disk Usage)**
- st_outbox grows if relay worker falls behind (100 events/sec × 60s = 6,000 rows)
- Sent events need cleanup (DELETE WHERE status='SENT' AND sent_at < NOW() - INTERVAL '7 days')
- **Mitigation**: Daily cleanup job (delete sent events older than 7 days)

⚠️ **6× Database Writes (Overhead)**
- Each P02 event → 6 st_outbox INSERTs (~9ms overhead)
- Higher than direct NATS publish (5ms)
- **Mitigation**: Batch outbox writes (single transaction for 6 events = ~9ms total)

⚠️ **Topic Proliferation**
- 6 topics per P02 event → topic management overhead
- Topic schema evolution requires coordination
- **Mitigation**: Centralized topic registry (k0/bus/topics.yaml), schema versioning

## Performance Analysis

### Latency Breakdown (10ms P95 Target)

| Operation                     | Latency (ms) | Notes                                   |
|-------------------------------|--------------|------------------------------------------|
| Build 6 event payloads        | 1-2          | JSON serialization                      |
| BEGIN transaction             | 0.5          | PostgreSQL transaction start            |
| st_outbox INSERT (6 events)   | 6-9          | 6 events × 1.5ms/event (batched)       |
| COMMIT                        | 1-2          | WAL write + fsync                       |
| **Total (M17)**               | **8.5-13ms** | P95 ~10ms                               |

**Relay Worker Latency** (eventual consistency):
- Poll interval: 100ms (configurable)
- NATS publish (6 events): 6×1ms = 6ms
- Update status (6 events): 6×1ms = 6ms
- **Total: 100ms + 12ms = 112ms** (P50 delivery latency)

### Throughput Analysis

**M17 Throughput**:
- 10ms per M17 execution → 100 executions/sec (1 connection)
- 10 connections → 1,000 executions/sec
- Each execution = 6 events → **6,000 events/sec** (outbox writes)

**Relay Worker Throughput**:
- Batch size: 128 messages
- Publish + update: 128 × 2ms = 256ms per batch
- Throughput: 1 batch/256ms = 3.9 batches/sec → **500 messages/sec** (1 worker)
- 10 workers → **5,000 messages/sec** (relay capacity)

**Bottleneck**: Relay worker (500 msg/sec) < M17 (6,000 msg/sec)
- **Mitigation**: Deploy 12+ relay workers to match M17 throughput

### st_outbox Growth Rate

**Growth Calculation**:
- P02 throughput: 100 events/sec
- 6 outbox entries per event = 600 rows/sec
- Daily growth: 600 × 86,400 = **51.8M rows/day** (before cleanup)
- Sent events deleted after 7 days → steady state ~360M rows

**Disk Usage**:
- Average row size: 500 bytes (JSON payload)
- 360M rows × 500 bytes = **180 GB** (steady state)
- **Mitigation**: Daily cleanup (delete sent events >7 days old)
