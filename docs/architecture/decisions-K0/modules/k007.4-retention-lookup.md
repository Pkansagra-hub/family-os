# k007.4 - Retention Lookup (Lifecycle Policy Resolution)

**Status**: ACCEPTED | **Parent**: [k007 - Context Enrichment Architecture](k007-context-enrichment.md)

---

## Executive Summary

**M11 (Retention Lookup)** resolves retention policy at write time using a 3-axis matrix lookup (band × topic × device_kind) for GDPR compliance and lifecycle management.

**Key Design Points**:
1. **Matrix Lookup**: (band, topic, device_kind) → retention_policy_id
2. **Retention Buckets**: STANDARD (routine), SENSITIVE (audit required)
3. **Fallback Chain**: (band,topic,device) → (band,topic,*) → (band,*,*)
4. **Cache Strategy**: 10-minute TTL, invalidate on policy updates
5. **GDPR Fields**: retention_days, deletion_eligible_at timestamp

**Performance Budget**: <3ms P95 (cache-optimized lookup)

---

## Context

### Lifecycle Management Problem

Episodic memories have different lifecycle requirements:
- **RED band meal events**: Keep 30 days (GDPR right to erasure)
- **AMBER band conversation events**: Keep 90 days (standard retention)
- **GREEN band milestone events**: Keep 7 years (long-term memory)
- **RED band voice import**: Keep 7 days (transcription data, short retention)

**Retention varies by**:
1. **Privacy Band**: RED (high privacy) → shorter retention
2. **Ingress Topic**: voice imports (ephemeral) vs. milestones (long-term)
3. **Device Kind**: Watch fitness data (short) vs. phone journal (long)

### GDPR Compliance

Article 17 (Right to Erasure):
> "The data subject shall have the right to obtain from the controller the erasure of personal data without undue delay."

**Requirements**:
- Store `retention_days` for each event (7/30/90/365/2555 days)
- Precompute `deletion_eligible_at` timestamp (event_time + retention_days)
- Automatic deletion batch process (P12 - Lifecycle Management)
- Audit log for deletions (compliance proof)

### Retention Policy Matrix

**Lookup Key**: `(band, ingress_topic, device_kind)` → `retention_policy_id`

| Band | Topic | Device | Retention Days | Bucket | Policy ID |
|------|-------|--------|----------------|--------|------------|
| RED | cognitive.memory.write | phone | 30 | STANDARD | pol-001 |
| RED | cognitive.memory.write | watch | 7 | STANDARD | pol-002 |
| RED | cognitive.memory.voice | * | 7 | SENSITIVE | pol-003 |
| AMBER | cognitive.memory.write | * | 90 | STANDARD | pol-004 |
| AMBER | cognitive.memory.photo | * | 365 | STANDARD | pol-005 |
| GREEN | cognitive.memory.write | * | 2555 | STANDARD | pol-006 |

**Fallback Chain**:
1. Try `(band, topic, device_kind)`: pol-001 ✅
2. If no match, try `(band, topic, *)`: pol-004 ✅
3. If no match, try `(band, *, *)`: pol-default ✅
4. If still no match, use system default: 90 days

**Retention Buckets**:
- **STANDARD**: Routine content (no special handling)
- **SENSITIVE**: Requires deletion audit trail (voice transcriptions, health data)

## Decision

### Algorithm

```python
async def lookup_retention_policy(
    band: str,
    ingress_topic: str,
    device_kind: str,
    cache: RedisCache
) -> RetentionPolicy:
    """
    Resolve retention policy using 3-axis matrix lookup with fallback.

    Performance: <3ms P95 (cache-optimized)
    """
    # Step 1: Try exact match (band, topic, device_kind)
    cache_key = f"retention:{band}:{ingress_topic}:{device_kind}"
    policy = await cache.get(cache_key)
    if policy:
        return policy

    # Step 2: Database lookup with fallback chain
    policy = await db.execute(
        """
        SELECT retention_policy_id, retention_days, retention_bucket
        FROM st_retention_policies
        WHERE band = :band
          AND (ingress_topic = :topic OR ingress_topic = '*')
          AND (device_kind = :device OR device_kind = '*')
        ORDER BY
          -- Prioritize exact match
          CASE
            WHEN ingress_topic = :topic AND device_kind = :device THEN 1
            WHEN ingress_topic = :topic AND device_kind = '*' THEN 2
            WHEN ingress_topic = '*' AND device_kind = '*' THEN 3
          END
        LIMIT 1
        """,
        {"band": band, "topic": ingress_topic, "device": device_kind}
    ).fetchone()

    # Step 3: Fallback to system default (90 days STANDARD)
    if not policy:
        policy = RetentionPolicy(
            retention_policy_id="pol-default",
            retention_days=90,
            retention_bucket="STANDARD"
        )

    # Step 4: Cache result (10-minute TTL)
    await cache.set(cache_key, policy, ttl=600)

    return policy
```

### Precompute Deletion Timestamp

```python
def compute_deletion_eligible_at(
    event_time_utc: datetime,
    retention_days: int
) -> datetime:
    """
    Precompute deletion eligibility timestamp.

    GDPR compliance: deletion_eligible_at = event_time + retention_days
    """
    return event_time_utc + timedelta(days=retention_days)
```

### Cache Invalidation

```python
async def invalidate_retention_cache(
    band: Optional[str] = None,
    ingress_topic: Optional[str] = None,
    device_kind: Optional[str] = None
):
    """
    Invalidate cache when retention policies change.

    Use cases:
    - Admin updates retention policy for RED band meals: Invalidate retention:RED:cognitive.memory.write:*
    - New retention policy added: Invalidate all matching keys
    """
    pattern = f"retention:{band or '*'}:{ingress_topic or '*'}:{device_kind or '*'}"
    await cache.delete_pattern(pattern)
```

## Alternatives Considered

### Alternative 1: Single Global Retention (Rejected)

**Approach**: All events have same retention (e.g., 90 days).

**Pros**: Simplest implementation

**Cons**:
- ❌ GDPR risk: RED band data kept too long (privacy violation)
- ❌ Storage waste: GREEN band milestones deleted too early
- ❌ No compliance flexibility: Cannot adjust retention per data type

**Rejected**: GDPR requires data-type-specific retention.

### Alternative 2: Compute Retention at Query Time (Rejected)

**Approach**: No retention_policy_id at write time, compute during query.

**Pros**: No upfront lookup cost

**Cons**:
- ❌ Query complexity: Every query must JOIN st_retention_policies
- ❌ Deletion process: Cannot efficiently find deletion candidates (no precomputed deletion_eligible_at)
- ❌ GDPR violation: Cannot guarantee timely deletion (no proactive timestamp)

**Rejected**: Precomputing deletion_eligible_at essential for GDPR compliance.

### Alternative 3: Retention in ACL Rules (Rejected)

**Approach**: Embed retention logic in ACL module (k005.1).

**Pros**: Single policy evaluation point

**Cons**:
- ❌ ACL bloat: Mixing WHO-sees (ACL) with HOW-LONG (retention)
- ❌ No device/topic context: ACL only knows band, not ingress_topic/device_kind
- ❌ Coupling: ACL changes affect retention (tight coupling)

**Rejected**: Retention orthogonal to access control (separate concerns).

### Alternative 4: Chosen - Matrix Lookup with Cache

**Pros**:
- ✅ <3ms P95 (cache-optimized)
- ✅ GDPR compliant (precomputed deletion_eligible_at)
- ✅ Flexible: Admin can adjust policies without code changes
- ✅ Fallback chain: Graceful degradation (exact → wildcard → default)

**Cons**:
- ⚠️ Cache invalidation complexity (on policy updates)
- ⚠️ Storage overhead (retention_policy_id + retention_days per event)

**Why Chosen**: GDPR compliance requires precomputed timestamps, cache makes it fast.

## Consequences

### Positive

✅ **GDPR Compliant**: Precomputed deletion_eligible_at enables timely erasure
✅ **Fast Lookup**: <3ms P95 (cache-optimized)
✅ **Flexible Policies**: Admin adjusts without code changes
✅ **Fallback Safety**: Wildcard matches prevent policy gaps

### Negative (with Mitigations)

⚠️ **Cache Invalidation Complexity**: Policy updates must invalidate affected keys
- **Mitigation**: Subscribe to st_retention_policies updates, invalidate pattern-based keys
- **Monitoring**: Track cache hit rate (alert if <80%)

⚠️ **Storage Overhead**: 3 extra columns per event (retention_policy_id, retention_days, deletion_eligible_at)
- **Mitigation**: Storage cost acceptable (12 bytes × 10M events = 120MB)
- **Benefit**: Enables efficient deletion batch process (index on deletion_eligible_at)

⚠️ **Policy Matrix Maintenance**: Admin must define policies for all (band, topic, device) combinations
- **Mitigation**: Wildcard fallback chain (band,*,*) provides defaults
- **Tooling**: Admin UI to visualize policy matrix, highlight gaps

### Performance

| Operation | P50 | P95 | P99 |

| Cache hit | 0.5ms | 1.0ms | 1.5ms |

| Cache set | 0.5ms | 1.0ms | 1.5ms |
| **Total (cached)** | **1.0ms** | **2.0ms** | **3.0ms** |

**Cache hit rate target**: >80% (after warmup)

## Testing Strategy

```python
def test_matrix_lookup_exact_match():
    policy = await lookup_retention_policy("RED", "cognitive.memory.write", "phone", cache)
    assert policy.retention_policy_id == "pol-001"
    assert policy.retention_days == 30

def test_matrix_lookup_fallback():
    policy = await lookup_retention_policy("RED", "cognitive.memory.unknown", "phone", cache)
    assert policy.retention_policy_id == "pol-default-red"

def test_deletion_timestamp():
    event_time = datetime(2025, 11, 16, 12, 0, 0, tzinfo=timezone.utc)
    deletion_at = compute_deletion_eligible_at(event_time, 30)
    expected = datetime(2025, 12, 16, 12, 0, 0, tzinfo=timezone.utc)
    assert deletion_at == expected
```
