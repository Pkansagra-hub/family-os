# k008.1 - Family Graph Resolver (Social Context Attribution)

**Status**: ACCEPTED | **Parent**: [k008 - Social Graph Architecture](k008-social-graph.md)

---

## Executive Summary

**M07 (Family Graph Resolver)** queries the family relationship graph to enrich episodic memories with social context, enabling social-importance salience scoring and family dynamics analysis.

**Key Design Points**:
1. **5 Relationship Types**: SPOUSE_OF, PARENT_OF, CHILD_OF, CARETAKER_OF, SIBLING_OF
2. **Social Context Classification**: solo, nuclear_family, extended_family, friends, work
3. **Intimacy Scoring**: HIGH (nuclear family), MED (extended family), LOW (acquaintances)
4. **Cached Lookups**: <8ms P95 (indexed st_relationships queries)
5. **Privacy-Preserving**: Never expose relationships outside visibility scope

**Performance Budget**: <8ms P95 (cached graph lookup)

---

## Context

### Social Context Problem

Episodic memories occur in social contexts that affect salience:
- **Solo event**: "Morning coffee alone" (LOW salience, routine)
- **Partner present**: "Dinner with spouse" (HIGH salience, family bonding)
- **Nuclear family**: "Birthday party with kids" (HIGH salience, milestone)
- **Extended family**: "Reunion with grandparents" (MED salience, special occasion)

**Social context affects**:
- **Salience scoring**: Nuclear family events score higher (social_importance = 1.0)
- **Memory prioritization**: High-intimacy events recalled more often
- **Privacy**: Family relationships influence visibility (spouse can see more than friends)

### Relationship Types

**5 Basic Relationships** (from `st_relationships`):

| Type | Definition | Example | Intimacy |
|------|------------|---------|----------|
| SPOUSE_OF | Married/partner | Prince ↔ Jeel | HIGH |
| PARENT_OF | Parent-child | Prince → Sharvi | HIGH |
| CHILD_OF | Inverse of PARENT_OF | Sharvi → Prince | HIGH |
| CARETAKER_OF | Guardian/caregiver | Grandparent → Sharvi | MED |
| SIBLING_OF | Brother/sister | (future) | MED |

**Graph Characteristics**:
- **Bidirectional**: SPOUSE_OF, SIBLING_OF
- **Unidirectional**: PARENT_OF, CHILD_OF, CARETAKER_OF
- **Transitive**: Can traverse multi-hop (e.g., spouse's parent = in-law)
- **Cached**: `st_relationships` table seeded from migration 0018, extended in 0024

### Social Context Classification

| Context | Definition | Examples | Use Case |
|---------|------------|----------|----------|
| solo | No other participants | "Morning shower", "Solo walk" | Routine detection |
| nuclear_family | Spouse, parents, children | "Dinner with spouse + kids" | High salience |
| extended_family | Grandparents, aunts, uncles | "Holiday with grandparents" | Medium salience |
| friends | Non-family social | "Coffee with friend" | Social tracking |
| work | Professional relationships | "Client meeting" | Work-life balance |

**Classification Rules**:
1. If `num_participants == 1` → `solo`
2. If any participant is SPOUSE_OF, PARENT_OF, CHILD_OF → `nuclear_family`
3. If any participant is CARETAKER_OF, SIBLING_OF → `extended_family` (unless nuclear_family)
4. If no family relationships found → `friends` (default for social events)
5. If event occurs during work hours + work location → `work` (heuristic)

## Decision

### Algorithm

```python
async def resolve_family_graph(
    actor_id: str,
    participants: list[str],
    cache: RedisCache
) -> SocialContext:
    """
    Resolve social context from family graph.

    Performance: <8ms P95 (cached relationships)
    """
    # Step 1: Handle solo events
    if not participants or len(participants) == 1:
        return SocialContext(
            num_participants=1,
            is_solo_event=True,
            social_context="solo",
            social_intimacy="LOW",
            has_partner_present=False,
            has_parent_present=False,
            participant_roles_json={"actor": actor_id}
        )

    # Step 2: Query relationships (cached)
    cache_key = f"relationships:{actor_id}"
    relationships = await cache.get(cache_key)
    if not relationships:
        relationships = await db.execute(
            """
            SELECT related_person_id, relationship_type
            FROM st_relationships
            WHERE person_id = :actor_id
            """,
            {"actor_id": actor_id}
        ).fetchall()
        await cache.set(cache_key, relationships, ttl=300)  # 5-minute TTL

    # Step 3: Classify participant roles
    participant_roles = {}
    has_partner = False
    has_parent = False
    has_nuclear_family = False
    has_extended_family = False

    for participant_id in participants:
        if participant_id == actor_id:
            participant_roles[participant_id] = "SELF"
            continue

        rel_type = find_relationship(relationships, participant_id)
        if rel_type == "SPOUSE_OF":
            participant_roles[participant_id] = "SPOUSE"
            has_partner = True
            has_nuclear_family = True
        elif rel_type == "PARENT_OF":
            participant_roles[participant_id] = "CHILD"
            has_nuclear_family = True
        elif rel_type == "CHILD_OF":
            participant_roles[participant_id] = "PARENT"
            has_parent = True
            has_nuclear_family = True
        elif rel_type == "CARETAKER_OF":
            participant_roles[participant_id] = "CAREGIVER"
            has_extended_family = True
        elif rel_type == "SIBLING_OF":
            participant_roles[participant_id] = "SIBLING"
            has_extended_family = True
        else:
            participant_roles[participant_id] = "OTHER"

    # Step 4: Determine social context
    if has_nuclear_family:
        social_context = "nuclear_family"
        social_intimacy = "HIGH"
    elif has_extended_family:
        social_context = "extended_family"
        social_intimacy = "MED"
    else:
        social_context = "friends"
        social_intimacy = "LOW"

    return SocialContext(
        num_participants=len(participants),
        is_solo_event=False,
        social_context=social_context,
        social_intimacy=social_intimacy,
        has_partner_present=has_partner,
        has_parent_present=has_parent,
        participant_roles_json=participant_roles
    )
```

## Alternatives Considered

### Alternative 1: No Social Context (Rejected)

**Approach**: Store no social metadata, treat all events as context-free.

**Pros**: Simplest implementation

**Cons**:
- ❌ Loses family dynamics (cannot distinguish solo vs. family events)
- ❌ Salience scoring less accurate (no social_importance factor)
- ❌ Cannot prioritize high-intimacy memories

**Rejected**: Social context essential for salience and memory prioritization.

### Alternative 2: Query st_relationships Every Event (Rejected)

**Approach**: No caching, query relationships table on every P02 event write.

**Pros**: Always fresh data

**Cons**:
- ❌ Latency: 15-30ms per event (DB query overhead)
- ❌ Database load: 10K events/day × queries
- ❌ Unnecessary: Relationships rarely change (cached approach sufficient)

**Rejected**: Caching provides <8ms P95 vs. 15-30ms without cache.

### Alternative 3: Precompute All Relationships (Rejected)

**Approach**: Precompute all possible participant combinations → social_context.

**Pros**: O(1) lookup

**Cons**:
- ❌ Storage explosion: N participants × M relationships = combinatorial
- ❌ Maintenance: Every relationship change triggers recomputation
- ❌ Overkill: Most events have 1-3 participants (simple lookup sufficient)

**Rejected**: Cache-based lookup is fast enough (<8ms P95).

### Alternative 4: Chosen - Cached Graph Lookup

**Pros**:
- ✅ <8ms P95 (cached relationships)
- ✅ Rich social context (5 relationship types)
- ✅ Privacy-preserving (never expose relationships outside visibility)
- ✅ Flexible: Can add new relationship types without schema changes

**Cons**:
- ⚠️ Cache invalidation complexity (on relationship changes)
- ⚠️ 5-minute cache lag (acceptable for family relationships)

**Why Chosen**: Fast, accurate, good enough for P02 write path.

---

## Consequences

### Positive

✅ **Fast Lookup**: <8ms P95 (cached relationships)
✅ **Rich Social Context**: 5 relationship types enable nuanced classification
✅ **Salience Ready**: social_intimacy feeds into salience scoring
✅ **Privacy-Preserving**: Never expose relationships outside visibility scope

### Negative (with Mitigations)

⚠️ **Cache Invalidation Complexity**: Relationship changes require cache invalidation
- **Mitigation**: Subscribe to st_relationships updates, invalidate affected person_ids
- **Monitoring**: Track cache hit rate (alert if <80%)

⚠️ **5-Minute Cache Lag**: New relationships take up to 5 minutes to appear
- **Mitigation**: Acceptable (relationships change rarely, minutes of lag is tolerable)
- **Alternative**: Reduce TTL to 60 seconds if needed (increases DB load)

⚠️ **Privacy Leakage Risk**: Relationship graph reveals sensitive connections
- **Mitigation**:
  - Never expose `participant_roles_json` outside event's visibility scope
  - ACL checks before returning social context
  - Audit log all relationship queries

### Performance

| Operation | P50 | P95 | P99 |
|-----------|-----|-----|-----|
| Cache hit | 1.0ms | 2.0ms | 3.0ms |
| DB query (cache miss) | 10ms | 20ms | 30ms |
| **Total (cached)** | **1.5ms** | **3.0ms** | **5.0ms** |

**Cache hit rate target**: >80% (after warmup)
