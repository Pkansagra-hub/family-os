# k003.3 - CA3 Clustering Service (Pattern Discovery)

**Status**: ACCEPTED | **Parent**: [k003 - Hippocampus Architecture](k003-hippocampus-architecture.md)

---

## Executive Summary

**CA3Service (M03)** performs **episode clustering and near-duplicate detection** in the **P03 Consolidation Pipeline** (background processing). This module reads SimHash/MinHash fingerprints produced by k003.1 (DG Pattern Separation) and groups similar episodes into clusters, detects near-duplicates, and scores novelty.

**Key Design Points**:

1. **Hamming Distance Neighbor Queries**: Find near-duplicates using SimHash with ≤4 bits difference (LSH bucketing for O(log n) queries)
2. **Jaccard Similarity via MinHash**: Compute similarity estimates using MinHash signatures (threshold: >0.8 for clustering)
3. **Greedy Agglomerative Clustering**: Start-of-implementation approach (upgradeable to DBSCAN for arbitrary cluster shapes)
4. **Novelty Scoring**: Quantify how different an episode is from existing clusters (0.0 = duplicate, 1.0 = completely novel)
5. **Background Processing**: No strict latency requirements (P03 runs asynchronously, not in write path)

**Performance Budget**: Throughput 10K events/day per tenant, memory <500MB for clustering state.

---

## Context

### The Episode Clustering Problem

After P02 writes episodic events with DG fingerprints (SimHash + MinHash), we need to:

1. **Find near-duplicates**: Multiple ingress paths may create duplicate events (e.g., calendar sync + manual entry)
2. **Cluster similar episodes**: Group related events (e.g., all "family dinners at home" form a cluster)
3. **Score novelty**: Detect truly novel experiences vs. routine patterns (e.g., "first trip to Japan" vs. "daily commute")
4. **Support memory consolidation**: Enable P03 to prioritize novel events for long-term retention

Unlike DG pattern separation (k003.1), which operates in the write path (<15ms), CA3 clustering is a **background process** with relaxed latency requirements.

### Biological Inspiration: CA3 Autoassociative Network

In the hippocampus, **CA3** is an autoassociative recurrent network that:

- **Completes patterns** from partial cues (pattern completion)
- **Separates overlapping patterns** using recurrent collateral connections
- **Supports episodic recall** by linking similar memory traces
- **Enables consolidation** of memories into neocortical long-term storage

Our CA3Service mimics this by:

- Using **LSH-based neighbor queries** (pattern completion via similarity search)
- Applying **clustering algorithms** to group related episodes (pattern separation at the cluster level)
- Supporting **P03 consolidation** by identifying which memories are novel enough to warrant long-term storage

### Performance Requirements

Unlike write-path modules (DG <15ms, CA1 <20ms), CA3 operates in **P03 background pipeline**:

- **No strict P95/P99 latency**: Batch processing acceptable
- **Throughput**: 10K events/day per tenant (~7 events/minute)
- **Memory**: <500MB for clustering state (tenant-isolated)
- **Scalability**: Algorithm must support millions of events over time (requires LSH indexing)

### Why Not Cluster in P02 Write Path?

Clustering requires **global view** of all events:

- **O(n) neighbor queries**: Checking every event against all existing events is too slow for write path
- **Cluster stability**: Clusters evolve as new events arrive; write-time clustering would be unstable
- **Latency budget**: P02 must complete in <100ms total; clustering could take seconds per event

By deferring to P03:

- P02 writes **only fingerprints** (SimHash/MinHash), keeping write path fast
- P03 reads fingerprints in batches and performs clustering with relaxed latency
- Cluster IDs are back-propagated to `st_hipp_events` via UPDATE queries

### Algorithm: Three-Phase Clustering Process

#### Phase 1: Near-Duplicate Detection (Hamming Distance)

**Input**: `simhash_64` (64-bit hex string from k003.1)
**Output**: `near_duplicates` (JSON array of event IDs with Hamming distance ≤4)

```python
def find_near_duplicates(target_simhash: str, events: List[Event]) -> List[NearDuplicate]:
    """
    Find events with Hamming distance ≤ 4 bits from target.
    Uses LSH bucketing for O(log n) queries (instead of O(n) linear scan).
    """
    target_bits = int(target_simhash, 16)
    near_duplicates = []

    # Query LSH buckets (16 buckets using 4-bit prefix)
    bucket_prefix = target_simhash[:1]  # First hex digit (4 bits)
    candidate_events = lsh_index.get_bucket(bucket_prefix)

    for event in candidate_events:
        event_bits = int(event.simhash_64, 16)
        hamming_dist = bin(target_bits ^ event_bits).count('1')

        if hamming_dist <= 4:  # Near-duplicate threshold
            near_duplicates.append({
                'event_id': event.event_id,
                'hamming_distance': hamming_dist,
                'similarity_estimate': 1.0 - (hamming_dist / 64.0)  # 0.94+ similarity
            })

    return sorted(near_duplicates, key=lambda x: x['hamming_distance'])
```

**Why Hamming Distance ≤4 bits?**

| Hamming Distance | Similarity Estimate | Interpretation |
|-----------------|---------------------|----------------|
| 0 bits | 100% | Exact duplicate (same SimHash) |
| 1-2 bits | 97-98% | Near-duplicate (minor text variation) |
| 3-4 bits | 94-95% | Very similar (same event, different phrasing) |
| 5-8 bits | 87-93% | Similar topic (e.g., two family dinners) |
| >8 bits | <87% | Different events |

Threshold of 4 bits balances precision (few false positives) with recall (catches most duplicates).

#### Phase 2: Similarity Estimation (Jaccard via MinHash)

**Input**: `minhash_32` (32 permutation hashes from k003.1)
**Output**: Jaccard similarity estimate (0.0-1.0)

```python
def estimate_jaccard_similarity(minhash_a: List[int], minhash_b: List[int]) -> float:
    """
    Estimate Jaccard similarity using MinHash signatures.
    Accuracy: E[estimate] = true_jaccard (unbiased estimator).
    """
    if len(minhash_a) != len(minhash_b):
        raise ValueError("MinHash signatures must have same length")

    matches = sum(1 for i in range(len(minhash_a)) if minhash_a[i] == minhash_b[i])
    return matches / len(minhash_a)  # Fraction of matching min-hashes
```

**Clustering Threshold**: Jaccard similarity >0.8

- **>0.8 similarity**: High overlap in 3-gram shingles → Same cluster
- **0.6-0.8 similarity**: Related events → Potential sub-clusters
- **<0.6 similarity**: Different patterns → Separate clusters

#### Phase 3: Greedy Agglomerative Clustering

**Input**: Events with MinHash signatures
**Output**: Cluster assignments + confidence scores

```python
def greedy_agglomerative_cluster(events: List[Event], threshold: float = 0.8) -> Dict[str, ClusterAssignment]:
    """
    Greedy clustering: Assign each event to first cluster with similarity > threshold.
    If no match, create new cluster.
    """
    clusters = {}  # cluster_id -> representative MinHash
    assignments = {}  # event_id -> ClusterAssignment

    for event in sorted(events, key=lambda e: e.event_time_utc):  # Process chronologically
        best_cluster = None
        best_similarity = 0.0

        # Find best matching cluster
        for cluster_id, representative_minhash in clusters.items():
            similarity = estimate_jaccard_similarity(event.minhash_32, representative_minhash)
            if similarity > threshold and similarity > best_similarity:
                best_cluster = cluster_id
                best_similarity = similarity

        if best_cluster:
            # Assign to existing cluster
            assignments[event.event_id] = ClusterAssignment(
                cluster_id=best_cluster,
                confidence=best_similarity,
                novelty_score=1.0 - best_similarity  # Lower novelty for similar events
            )
        else:
            # Create new cluster (novel pattern)
            new_cluster_id = f"cluster_{uuid.uuid4().hex[:8]}"
            clusters[new_cluster_id] = event.minhash_32
            assignments[event.event_id] = ClusterAssignment(
                cluster_id=new_cluster_id,
                confidence=1.0,  # First event in cluster = perfect match
                novelty_score=1.0  # Completely novel (new cluster)
            )

    return assignments
```

**Why Greedy Clustering?**

- **Simple and fast**: O(n × k) where k = number of clusters (typically k << n)
- **Deterministic**: Same input → same clusters (important for reproducibility)
- **Good enough for start**: Can upgrade to DBSCAN later for arbitrary cluster shapes

**Limitations of Greedy Approach**:

- **Order-dependent**: Earlier events influence cluster structure
- **No cluster merging**: Cannot combine clusters after creation
- **Fixed threshold**: May miss subtle cluster boundaries

**Future Upgrade: DBSCAN (Density-Based Clustering)**:

- **Advantages**: Finds arbitrary shapes, handles noise, no fixed k
- **Trade-off**: More complex, requires density parameter tuning

### Novelty Scoring Algorithm

**Novelty Score** quantifies how different an event is from existing patterns:

```python
def compute_novelty_score(event: Event, near_duplicates: List[NearDuplicate], cluster_confidence: float) -> float:
    """
    Novelty = 1.0 - max_similarity_to_existing_events

    0.0 = Exact duplicate (near_duplicates with hamming_distance=0)
    0.3 = Similar to cluster (cluster_confidence=0.7)
    0.7 = Loosely related (cluster_confidence=0.3)
    1.0 = Completely novel (new cluster, no near-duplicates)
    """
    if near_duplicates:
        max_similarity = max(nd['similarity_estimate'] for nd in near_duplicates)
        return 1.0 - max_similarity
    else:
        # No near-duplicates, use cluster confidence as proxy
        return 1.0 - cluster_confidence
```

**Novelty Score Use Cases**:

- **P03 Consolidation**: Prioritize high-novelty events for long-term retention
- **Salience Adjustment**: Boost salience for novel experiences (e.g., "first trip to Japan")
- **Deduplication**: Flag low-novelty events (novelty <0.1) as potential duplicates

**Novelty Score Edge Cases**:

**Case 1: Multiple Near-Duplicates** (which one to use?)
```python
near_duplicates = [
    {'event_id': 'evt_1', 'similarity': 0.98},  # Very close
    {'event_id': 'evt_2', 'similarity': 0.95},  # Close
    {'event_id': 'evt_3', 'similarity': 0.92}   # Similar
]
novelty = 1.0 - max(0.98, 0.95, 0.92)  # Use MAX similarity
# Result: 0.02 (near-duplicate)
```

**Case 2: In Cluster But No Near-Duplicates** (Hamming >4 but Jaccard >0.8)
```python
# Event has high Jaccard similarity to cluster (0.85) but Hamming >4 bits
# No near-duplicates flagged (Hamming threshold not met)
near_duplicates = []
cluster_confidence = 0.85

novelty = 1.0 - cluster_confidence
# Result: 0.15 (routine pattern, but no exact duplicate)
```

**Case 3: Novel Event Creates New Cluster**
```python
# First event of a new pattern (e.g., "first trip to Japan")
near_duplicates = []
cluster_confidence = 1.0  # Perfect match to self (new cluster representative)

# Special case: New cluster = high novelty
if is_new_cluster:
    novelty = 1.0  # Override cluster_confidence
else:
    novelty = 1.0 - cluster_confidence
# Result: 1.0 (completely novel)
```

**Case 4: Outlier vs. Novel** (DBSCAN noise point)
```python
# Event doesn't fit any cluster (outlier) but may not be novel
# Example: Corrupted text, spam, data quality issue
near_duplicates = []
cluster_confidence = 0.0  # No cluster match

# Outlier detection (future work):
if is_outlier(event):  # Check text quality, length, etc.
    novelty = 0.5  # Medium novelty (flag for manual review)
else:
    novelty = 1.0  # Truly novel
```

### LSH Bucket Implementation Details

**Bucket Key Strategy**:
- Use first hex digit of SimHash (4 bits) as bucket key
- 16 possible buckets: `0x0` through `0xF`
- Expected bucket size: n/16 events (e.g., 100K events → ~6,250 per bucket)

**Index Structure**:
```python
class LSHIndex:
    def __init__(self):
        self.buckets: Dict[str, List[Event]] = defaultdict(list)  # hex_prefix → events

    def insert(self, event: Event):
        """Insert event into LSH bucket based on SimHash prefix."""
        bucket_key = event.simhash_64[0]  # First hex digit (4 bits)
        self.buckets[bucket_key].append(event)

    def query(self, target_simhash: str, threshold: int = 4) -> List[NearDuplicate]:
        """Query for near-duplicates within Hamming threshold."""
        bucket_key = target_simhash[0]
        candidates = self.buckets[bucket_key]  # O(1) lookup

        near_duplicates = []
        target_bits = int(target_simhash, 16)

        for event in candidates:
            event_bits = int(event.simhash_64, 16)
            hamming = bin(target_bits ^ event_bits).count('1')

            if hamming <= threshold:
                near_duplicates.append(NearDuplicate(
                    event_id=event.event_id,
                    hamming_distance=hamming,
                    similarity=1.0 - hamming/64.0
                ))

        return near_duplicates
```

**Bucket Distribution Analysis**:
- Uniform SimHash → uniform bucket distribution (each bucket ~n/16)
- Skewed real-world data → some buckets may have 2-3× average size
- Monitoring: Alert if any bucket exceeds 10K events (requires sub-bucketing)

**Multi-Probe LSH** (future optimization):
- Query adjacent buckets (XOR with 0x1, 0x2, 0x4, 0x8) to catch boundary cases
- Trade-off: 5× more candidates, but catches events near bucket boundaries

## Alternatives Considered

### Alternative 1: Cluster in P02 Write Path (Rejected)

**Approach**: Perform clustering synchronously during event write.

**Pros**:
- Immediate cluster assignment (no delay)
- Simpler data flow (no P03 back-propagation)

**Cons**:
- ❌ **Latency**: O(n) neighbor queries too slow for <100ms write budget
- ❌ **Instability**: Clusters change as new events arrive, causing churn
- ❌ **Scalability**: Write path cannot handle millions of event comparisons
- ❌ **Blocking**: Clustering failures would block event writes

**Rejection Rationale**: Write-path latency budget (<100ms total) cannot accommodate clustering queries. P02 must remain fast and predictable.

### Alternative 2: Embedding-Based Clustering (Rejected)

**Approach**: Use dense embeddings (6144-dim vectors) instead of SimHash/MinHash for clustering.

**Pros**:
- Higher semantic accuracy (captures deep meaning)
- No hash collisions (continuous similarity space)

**Cons**:
- ❌ **Latency**: Embedding generation takes 200-500ms (GPU inference)
- ❌ **Storage**: 6144 bytes per event vs. 84 bytes for hashes (73× larger)
- ❌ **Complexity**: Requires vector search index (HNSW, Annoy)
- ❌ **Dependency**: Blocks on P08 embedding generation (eventual consistency issue)

**Rejection Rationale**: Embeddings are deferred to P08 (asynchronous pipeline). CA3 must operate on available fingerprints (SimHash/MinHash) for immediate clustering after P02 write.

### Alternative 3: No Clustering (Flat Storage) (Rejected)

**Approach**: Store all events without clustering; let queries do similarity search on demand.

**Pros**:
- Simplest approach (no clustering logic)
- No cluster maintenance overhead

**Cons**:
- ❌ **Query latency**: Every recall query must scan all events (O(n) per query)
- ❌ **No novelty detection**: Cannot identify duplicates or novel patterns
- ❌ **No consolidation support**: P03 cannot prioritize memories for retention
- ❌ **Poor UX**: User sees duplicate memories without deduplication

**Rejection Rationale**: Memory consolidation (P03) requires clustering to identify which events are novel enough to retain long-term. Flat storage loses neuroscience-inspired benefits.

### Alternative 4: DBSCAN Clustering (Deferred to v2)

**Approach**: Use density-based clustering (DBSCAN) instead of greedy agglomerative.

**Pros**:
- Finds arbitrary cluster shapes (not just spherical)
- Automatically identifies noise points (outliers)
- No need to specify number of clusters

**Cons**:
- ⚠️ **Complexity**: Requires epsilon (density radius) parameter tuning
- ⚠️ **Stability**: Small parameter changes can drastically alter clusters
- ⚠️ **Implementation time**: More complex than greedy clustering

**Decision**: Start with **greedy agglomerative** (simpler, deterministic), upgrade to DBSCAN in v2 if cluster quality issues arise.

**Migration Path**: Greedy → DBSCAN is non-breaking (just re-cluster existing events with new algorithm).

## Consequences

### Positive Consequences

✅ **Background Processing Eliminates Write-Path Latency**
- P02 writes fingerprints in <15ms; P03 clusters asynchronously
- No blocking on clustering queries during event ingestion

✅ **LSH Indexing Enables Scalability to Millions of Events**
- O(log n) neighbor queries instead of O(n) linear scan
- Supports 1M+ events per tenant without performance degradation

✅ **Novelty Scoring Enables Smart Consolidation**
- P03 can prioritize high-novelty events for long-term retention
- Low-novelty events (duplicates, routine patterns) can be compressed or discarded

✅ **Deterministic Clustering (Greedy Algorithm)**
- Same input → same clusters (important for reproducibility)
- No stochastic behavior (unlike k-means with random initialization)

### Negative Consequences (with Mitigations)

⚠️ **Eventual Consistency: Cluster IDs Not Available Immediately**
- **Issue**: Events written by P02 have NULL cluster_id until P03 runs (delay: 5-15 minutes)
- **Mitigation**: P02 queries (e.g., salience scoring) do not depend on clustering; P03 consolidation is the primary consumer

⚠️ **Greedy Clustering Is Order-Dependent**
- **Issue**: Event processing order affects cluster assignments (earlier events set cluster representatives)
- **Mitigation**: Process events chronologically (by `event_time_utc`) to ensure stable ordering; upgrade to DBSCAN in v2 if needed

⚠️ **Fixed Threshold (0.8 Jaccard) May Miss Cluster Boundaries**
- **Issue**: Some event pairs near 0.8 threshold may be mis-clustered
- **Mitigation**: Threshold tuning based on cluster quality metrics (silhouette score); future work: adaptive thresholds per tenant

⚠️ **No Hierarchical Clustering (Flat Clusters Only)**
- **Issue**: Cannot detect sub-episodes within larger events (e.g., "Italy vacation" containing "Venice day trip", "Rome dinner")
- **Mitigation**: Future work: hierarchical agglomerative clustering with dendrogram visualization

**Cluster Quality Metrics** (baseline targets):

**Silhouette Score** (measures cluster cohesion):
- **Formula**: `s(i) = (b(i) - a(i)) / max(a(i), b(i))`
  - `a(i)`: Avg distance to same-cluster events
  - `b(i)`: Avg distance to nearest-cluster events
- **Range**: -1 (wrong cluster) to +1 (perfect cluster)
- **Targets**:
  - >0.7: Excellent clustering (strong, well-separated clusters)
  - 0.5-0.7: Good clustering (acceptable separation)
  - 0.3-0.5: Weak clustering (overlapping clusters, consider DBSCAN)
  - <0.3: Poor clustering (re-tune threshold or switch algorithm)

**Dunn Index** (inter-cluster vs intra-cluster distance):
- **Formula**: `DI = min_inter_cluster_dist / max_intra_cluster_dist`
- **Range**: 0 (poor) to ∞ (perfect)
- **Targets**:
  - >2.0: Excellent separation
  - 1.0-2.0: Good separation
  - <1.0: Poor separation (clusters overlap)

**Precision/Recall for Near-Duplicates**:
- **Precision**: Fraction of flagged duplicates that are true duplicates
  - Target: >95% (low false positive rate)
- **Recall**: Fraction of true duplicates that are flagged
  - Target: >90% (catches most duplicates)
- **Manual Validation**: Sample 100 flagged duplicates, verify by human inspection

## Failure Modes & Mitigation

### 1. LSH Bucket Overflow (>10K events in single bucket)

**Symptom**: Query latency spikes from 50ms → 5000ms for affected bucket

**Root Cause**: Non-uniform SimHash distribution (e.g., all "family dinner" events hash to bucket `0x3`)

**Detection**:
```python
for bucket_key, events in lsh_index.buckets.items():
    if len(events) > 10_000:
        log.warning(f"Bucket {bucket_key} overflow: {len(events)} events")
```

**Mitigation**:
1. **Sub-bucket**: Split large bucket using second hex digit (16 → 256 buckets)
2. **Multi-probe LSH**: Query adjacent buckets to redistribute load
3. **Alert ops**: Manual investigation of data quality (spam, duplicates)

---

### 2. Cluster Drift (clusters change meaning over time)

**Symptom**: Silhouette score degrades from 0.7 → 0.4 over weeks

**Root Cause**: Greedy clustering is order-dependent; new events shift cluster boundaries

**Detection**:
```python
# Track silhouette score over time
daily_silhouette = compute_silhouette_score(all_events)
if daily_silhouette < 0.5:
    log.error(f"Cluster quality degraded: {daily_silhouette}")
```

**Mitigation**:
1. **Re-cluster periodically**: Monthly full re-clustering with stable data
2. **Upgrade to DBSCAN**: Density-based clustering more robust to ordering
3. **Cluster versioning**: Store `clustering_version` (e.g., "greedy_v1.0", "dbscan_v2.0")

---

### 3. Near-Duplicate False Negatives (missed duplicates)

**Symptom**: User reports seeing duplicate memories in timeline

**Root Cause**: Hamming threshold (≤4 bits) too strict for text variations

**Detection**:
```python
# Sample 100 events manually, check for missed duplicates
false_negative_rate = count_missed_duplicates / 100
if false_negative_rate > 0.10:  # >10% false negatives
    log.error(f"High false negative rate: {false_negative_rate}")
```

**Mitigation**:
1. **Increase threshold**: Try ≤5 or ≤6 bits (trade-off: more false positives)
2. **Multi-probe LSH**: Query adjacent buckets (catches boundary cases)
3. **Hybrid approach**: Use Jaccard (MinHash) as secondary check

---

### 4. P03 Batch Processing Lag

**Symptom**: Cluster IDs remain NULL for >30 minutes after P02 write

**Root Cause**: P03 throughput (10 events/sec) < P02 ingestion rate (20 events/sec)

**Detection**:
```python
unclustered_events = db.query(
    "SELECT COUNT(*) FROM st_hipp_events WHERE episode_cluster_id IS NULL"
)
if unclustered_events > 1000:
    log.error(f"P03 backlog: {unclustered_events} unclustered events")
```

**Mitigation**:
1. **Scale P03 workers**: Horizontal scaling (process batches in parallel)
2. **Batch size tuning**: Increase from 100 → 500 events per batch
3. **Priority queue**: Cluster high-salience events first (low-salience can wait)

---

### 5. Memory Exhaustion (>500MB clustering state)

**Symptom**: P03 worker crashes with OOM error

**Root Cause**: Tenant with 5M+ events exceeds memory budget

**Detection**:
```python
import psutil
memory_usage = psutil.Process().memory_info().rss / (1024 ** 2)  # MB
if memory_usage > 500:
    log.error(f"P03 memory usage: {memory_usage:.1f} MB")
```

**Mitigation**:
1. **Tenant isolation**: Cluster one tenant at a time (release memory between tenants)
2. **Incremental clustering**: Process events in 10K-event chunks
3. **Disk-backed index**: Use SQLite for LSH index (trade latency for memory)
