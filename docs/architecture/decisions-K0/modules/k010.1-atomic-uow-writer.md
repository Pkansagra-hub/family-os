# k010.1 - Atomic UnitOfWork Writer (P02 Storage Commit) - CORRECTED

**Status**: ACCEPTED | **Parent**: [k010 - Core Storage Writers Architecture](k010-core-writers.md)

**⚠️ Correction History**: Originally specified 3-table transaction; corrected to 2-table based on contract analysis (2025-11-16)

---

## Executive Summary

**M16 (Atomic UnitOfWork Writer)** commits P02-enriched events to persistent storage with **two-table atomicity**: st_hipp_events + st_pipeline_processed.

**Key Design Points**:
1. **Single Transaction**: st_hipp_events + st_pipeline_processed in one UnitOfWork (2 tables, NOT 3)
2. **Separate Writer**: M14 (embedding_queue_write) writes st_embedding_queue **independently** (separate transaction)
3. **Atomicity Guarantee**: Both tables succeed or both fail (no partial commits)
4. **Idempotency**: Check st_pipeline_processed BEFORE write to prevent duplicates
5. **Retry Strategy**: Exponential backoff for transient failures (max 3 attempts)
6. **Performance Target**: <30ms P95 for 2-table INSERT/UPSERT

**Transaction Semantics**: PostgreSQL READ COMMITTED isolation level, explicit BEGIN/COMMIT.

**Correction Note**: Initial design assumed M16 wrote all 3 tables. Contract analysis (milestone3_sketchboard.md Phase 7.1) revealed M14 contract has `side_effects: [write:st_embedding_queue]`, indicating direct write in separate transaction.

## Context

### Write Path Architecture (CORRECTED)

**P02 Pipeline Stages**:
```
WAL → M01-M12 (Enrichment) → M13 (Build Row) → M16 (Atomic Write: 2 tables) → M17 (Emit Events)
                                             ↓
                           M02 → M14 (Embedding Queue Write: separate transaction)
```

**M16 Responsibilities** (CORRECTED):
- **Input**: 1 dict from M13 (hipp_events_row)
- **Output**: 2 database writes in single transaction (st_hipp_events + st_pipeline_processed)
- **Guarantee**: Atomicity (both or neither)
- **Idempotency**: Skip duplicate writes via st_pipeline_processed

**M14 Responsibilities** (SEPARATE):
- **Input**: embedding_id from M02
- **Output**: 1 database write (st_embedding_queue)
- **Transaction**: Independent from M16 (can succeed/fail independently)

### Two-Table Write Problem (CORRECTED)

**Why 2 Tables in M16 Transaction?**

1. **st_hipp_events** (enriched episodic memory)
   - Primary storage for P02 output
   - 60-70 columns (identity, policy, temporal, spatial, social, affect, hippocampus)
   - READ by P03 (consolidation), P04 (working memory), query APIs

2. **st_pipeline_processed** (P02 idempotency tracking)
   - Offset tracking: (pipeline_id='P02_WRITE', space_id, wal_pos)
   - Prevents reprocessing on P02 restart/retry
   - Enables safe retries without duplicates

**Why st_embedding_queue is NOT in M16 Transaction**:

**Reason 1: M14 Contract Behavior**
- M14 contract shows `side_effects: [write:st_embedding_queue]`
- This indicates M14 writes directly (not via M16)
- Confirmed in milestone3_sketchboard.md Phase 7.1

**Reason 2: Operational Isolation**
- Embedding generation is **deferred work** (P08 pipeline), not critical path
- M14 failure should NOT block M16 memory commit
- P08 can handle missing embedding jobs gracefully

**Reason 3: Retry Independence**
- M14 can retry independently if embedding queue write fails
- M16 can commit memory even if M14 failed
- Loose coupling improves system resilience

**Atomicity Requirement**: If st_hipp_events succeeds but st_pipeline_processed fails → memory written but marked unprocessed (P02 retries). If st_pipeline_processed succeeds but st_hipp_events fails → WAL entry marked processed but no memory (data loss - transaction prevents this).

### UnitOfWork Pattern (CORRECTED)

**Database Transaction Lifecycle**:
```python
async with uow.begin():
    # 1. Idempotency check (READ st_pipeline_processed)
    if await uow.is_already_processed(pipeline_id, space_id, wal_pos):
        return  # Skip write, already committed

    # 2. Write st_hipp_events (INSERT)
    await uow.hipp_events.insert(row_dict)

    # 3. Write st_pipeline_processed (UPSERT)
    await uow.pipeline_processed.upsert(pipeline_id, space_id, wal_pos)

    # 5. Commit (all succeed or rollback)
    await uow.commit()
```

**Transaction Boundaries**:
- **BEGIN**: Start transaction (implicit with `uow.begin()`)
- **COMMIT**: All 3 writes persisted atomically
- **ROLLBACK**: On error, all changes discarded

### Performance Requirements

**Latency Budget**: <30ms P95
- st_hipp_events INSERT: ~10ms (60-70 columns, 5 indexes)
- st_embedding_queue INSERT: ~3ms (10 columns, 2 indexes)
- st_pipeline_processed UPSERT: ~5ms (4 columns, 2 indexes)
- Transaction overhead: ~5ms (BEGIN, COMMIT, fsync)
- Buffer: ~7ms (network, connection pool)

**Throughput Goal**: 100-200 events/sec (single-event writes), 1000+ events/sec (batch writes)

**Idempotency Check**: <5ms (indexed lookup on st_pipeline_processed)

### Failure Scenarios

**Transient Failures** (retry with backoff):
- Database connection timeout
- Deadlock (rare with P02 append-only pattern)
- Temporary disk I/O spike

**Permanent Failures** (drop and log):
- Constraint violation (duplicate event_id)
- Foreign key violation (invalid wal_pos)
- CHECK constraint failure (invalid enum values)

**Critical Failures** (alert ops):
- Disk full (ENOSPC)
- Database crash/restart
- Connection pool exhaustion

## Decision

### Atomic UnitOfWork with Idempotency Check

**Architecture**: Single database transaction encompassing 3 writes with pre-write idempotency check.

**Implementation Pattern**:

```python
# k0/modules/core/hipp_events_writer.py

async def run(message: Message, context: ModuleContext, **config) -> dict:
    """
    M16: Atomic UnitOfWork Writer

    Commits P02 writes in single transaction:
    - st_hipp_events (enriched episodic memory)
    - st_embedding_queue (P08 vector job)
    - st_pipeline_processed (idempotency offset)

    Returns:
        dict: {
            "event_id": str,
            "wal_pos": int,
            "committed_at": datetime,
            "idempotency_skipped": bool
        }
    """
    # Extract inputs from M13/M14 outputs
    hipp_events_row = message.get("hipp_events_row")  # From M13
    embedding_queue_job = message.get("embedding_queue_job")  # From M14

    pipeline_id = "P02_WRITE"
    space_id = hipp_events_row["space_id"]
    wal_pos = hipp_events_row["wal_pos"]
    event_id = hipp_events_row["event_id"]

    # Begin transaction
    async with context.uow.begin() as txn:
        # STEP 1: Idempotency check (indexed lookup, <5ms)
        already_processed = await txn.pipeline_processed.exists(
            pipeline_id=pipeline_id,
            space_id=space_id,
            wal_pos=wal_pos
        )

        if already_processed:
            context.log.info(
                "P02 idempotency skip",
                event_id=event_id,
                wal_pos=wal_pos,
                space_id=space_id
            )
            return {
                "event_id": event_id,
                "wal_pos": wal_pos,
                "idempotency_skipped": True
            }

        # STEP 2: INSERT st_hipp_events (~10ms)
        await txn.hipp_events.insert(hipp_events_row)

        # STEP 3: INSERT st_embedding_queue (~3ms)
        await txn.embedding_queue.insert(embedding_queue_job)

        # STEP 4: UPSERT st_pipeline_processed (~5ms)
        await txn.pipeline_processed.upsert({
            "pipeline_id": pipeline_id,
            "space_id": space_id,
            "wal_pos": wal_pos,
            "processed_at": context.now(),
            "event_id": event_id
        })

        # STEP 5: Commit (atomic, ~5ms)
        await txn.commit()

    context.log.info(
        "P02 storage committed",
        event_id=event_id,
        wal_pos=wal_pos,
        latency_ms=context.elapsed_ms()
    )

    return {
        "event_id": event_id,
        "wal_pos": wal_pos,
        "committed_at": context.now(),
        "idempotency_skipped": False
    }
```

**Transaction Isolation**: PostgreSQL READ COMMITTED
- Prevents dirty reads (uncommitted data)
- Allows concurrent P02 writers (different space_id)
- Minimal lock contention (append-only pattern)

**Error Handling with Retry**:

```python
from tenacity import retry, stop_after_attempt, wait_exponential
from psycopg.errors import DeadlockDetected, OperationalError

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=100, min=100, max=1000),
    retry=retry_if_exception_type((DeadlockDetected, OperationalError)),
    reraise=True
)
async def run_with_retry(message, context, **config):
    return await run(message, context, **config)
```

**Idempotency Guarantee**:
- **Check st_pipeline_processed BEFORE write** (not after)
- **Skip all 3 writes if already processed** (no partial retries)
- **Return success even on skip** (idempotent semantics)

**Batch Write Optimization** (future):
```python
# Single transaction for 128 events (10×-50× throughput boost)
async with context.uow.begin() as txn:
    for event in batch:
        await txn.hipp_events.insert(event.row)
        await txn.embedding_queue.insert(event.queue_job)
        await txn.pipeline_processed.upsert(event.offset)
    await txn.commit()
```

**Performance Optimization: Deferred Indexing**:
- **Write-time**: Skip index updates for bulk writes
- **Batch REINDEX**: Daily at 03:00 UTC (REINDEX CONCURRENTLY)
- **Trade-off**: Query performance vs. write throughput (P02 is write-heavy)

## Alternatives Considered

### Alternative 1: Separate Transactions per Table

**Approach**: 3 transactions (st_hipp_events, st_embedding_queue, st_pipeline_processed)

**Pros**:
- Simpler error handling (no rollback logic)
- Lower lock contention (shorter transactions)
- Partial success possible (some writes succeed)

**Cons**:
- ❌ **No atomicity**: st_hipp_events succeeds but st_embedding_queue fails → orphaned event
- ❌ **Inconsistent state**: Event stored but no P08 job → no embeddings
- ❌ **Complex recovery**: Need cleanup jobs to find orphaned events
- ❌ **Idempotency broken**: st_pipeline_processed succeeds but st_hipp_events fails → event lost

**Rejected**: P02 requires all-or-nothing semantics (atomicity is core requirement).

### Alternative 2: Write st_hipp_events First, Queue Later

**Approach**: Commit st_hipp_events immediately, enqueue st_embedding_queue in separate transaction

**Pros**:
- Fast commit for primary data (st_hipp_events)
- Embedding queue failures don't block P02
- Can retry queue writes independently

**Cons**:
- ❌ **Orphaned events**: st_hipp_events exists but no P08 job
- ❌ **Delayed vectors**: Embeddings never generated if queue write fails
- ❌ **Search inconsistency**: Event queryable by text but not by vector
- ❌ **Cleanup burden**: Need background job to detect missing queue entries

**Rejected**: Embedding generation is **critical path** for semantic search (not optional).

### Alternative 3: Eventual Consistency (Best-Effort Writes)

**Approach**: Write to st_hipp_events, emit event to queue topic, let P08 claim work from event stream

**Pros**:
- No database queue (st_embedding_queue)
- Event-driven architecture (loose coupling)
- Scalable (message broker handles backpressure)

**Cons**:
- ❌ **No work tracking**: Can't query "pending embeddings" count
- ❌ **Replay complexity**: Message broker retention vs. job retries
- ❌ **Duplicate jobs**: At-least-once delivery → duplicate embeddings
- ❌ **Observability loss**: No centralized job status table

**Rejected**: Work queue pattern (st_embedding_queue) provides better observability and control.

### Alternative 4: Two-Phase Commit (2PC)

**Approach**: Distributed transaction across st_hipp_events and st_embedding_queue with prepare/commit phases

**Pros**:
- Strongest atomicity guarantee (even across databases)
- Industry-standard protocol (XA transactions)

**Cons**:
- ❌ **50-100ms latency**: 2× network round trips (prepare → commit)
- ❌ **Blocking**: Coordinator failure blocks all participants
- ❌ **Overkill**: All 3 tables in same PostgreSQL database (no distribution)
- ❌ **Complexity**: Requires 2PC coordinator, recovery log

**Rejected**: Single-database transaction sufficient (PostgreSQL ACID guarantees).

## Consequences

### Positive

✅ **Atomicity Guarantee**
- All 3 writes succeed or all rollback (no partial state)
- st_hipp_events + st_embedding_queue + st_pipeline_processed consistency
- Safe retries without orphaned data

✅ **Idempotent Retry**
- st_pipeline_processed check BEFORE write
- Can retry P02 failures without duplicates
- Safe for Kubernetes restarts, network blips

✅ **Consistent State**
- Every st_hipp_events row has matching st_embedding_queue job
- P08 workers always find valid embedding requests
- No cleanup jobs needed for orphaned events

✅ **Fast Commit (<30ms P95)**
- Single transaction faster than 3 separate commits
- Reduced fsync overhead (1× vs. 3×)
- Batch optimization possible (128 events per UoW)

✅ **Observability**
- Transaction duration tracked (BEGIN → COMMIT latency)
- Rollback reasons logged (constraint violation, deadlock, etc.)
- Idempotency skip rate metric (reprocessing detection)

### Negative

⚠️ **Write Latency Includes All 3 INSERTs (~30-50ms)**
- Single slow write (e.g., st_hipp_events with 60 columns) blocks entire transaction
- Cannot parallelize writes (sequential within transaction)
- **Mitigation**: Batch writes (128 events per transaction) reduce per-event overhead

⚠️ **Blocking on Database Connection**
- P02 throughput limited by connection pool size (default 10-20 connections)
- Long transactions hold connections longer (30ms vs. 10ms)
- **Mitigation**: Connection pooling (PgBouncer), transaction pooling mode

⚠️ **Rollback Overhead on Failure**
- Constraint violation → rollback all 3 writes (wasted work)
- Deadlock detection → automatic rollback + retry
- **Mitigation**: Pre-validate constraints in M13 (catch errors before write)

⚠️ **Idempotency Check Latency (~5ms per event)**
- Every P02 event queries st_pipeline_processed
- High reprocessing rate → high check overhead
- **Mitigation**: Index on (pipeline_id, space_id, wal_pos) for <5ms lookup

⚠️ **No Partial Success Semantics**
- If st_embedding_queue write fails → entire event rejected (including st_hipp_events)
- Cannot "commit memory but skip embedding"
- **Mitigation**: This is **desired behavior** (embeddings are critical path)

## Performance Analysis

### Latency Breakdown (30ms P95 Target)

| Operation                     | Latency (ms) | Notes                                   |
|-------------------------------|--------------|------------------------------------------|
| BEGIN transaction             | 1-2          | PostgreSQL transaction start            |
| Idempotency check (SELECT)    | 3-5          | Indexed lookup on st_pipeline_processed |
| st_hipp_events INSERT         | 8-12         | 60-70 columns, 5 indexes                |
| st_embedding_queue INSERT     | 2-4          | 10 columns, 2 indexes                   |
| st_pipeline_processed UPSERT  | 3-5          | 4 columns, conflict resolution          |
| COMMIT + fsync                | 4-8          | WAL write, disk sync                    |
| **Total (single event)**      | **21-36ms**  | P95 ~30ms, P99 ~45ms                    |

**Batch Write (128 events)**:
- Total latency: ~200ms (128 events)
- Per-event latency: **1.6ms** (128× amortization)
- Throughput: 640 events/sec (single connection)

### Throughput Analysis

**Single-Event Writes**:
- 30ms per commit → 33 events/sec (1 connection)
- 10 connections → 330 events/sec
- 20 connections → 660 events/sec

**Batch Writes (128 events/batch)**:
- 200ms per batch → 5 batches/sec → 640 events/sec (1 connection)
- 10 connections → 6,400 events/sec
- 20 connections → 12,800 events/sec

**P02 Throughput Target**: 100-200 events/sec (single-event), 1000+ events/sec (batched)

### Index Impact

**st_hipp_events Indexes** (5 total):
1. PRIMARY KEY (event_id) — btree
2. (space_id, event_time_utc) — btree (query optimization)
3. (actor_id, event_time_utc) — btree (actor timeline)
4. (simhash_hex) — hash (P03 near-duplicate lookup)
5. (wal_pos) — btree (P02 offset tracking)

**Index Update Overhead**:
- 5 indexes × 2ms/index = 10ms (part of INSERT latency)
- **Deferred indexing option**: Skip index updates during bulk writes, REINDEX daily

**st_embedding_queue Indexes** (2 total):
1. PRIMARY KEY (embedding_id) — btree
2. (status, priority, created_at) — btree (P08 job claim query)

**st_pipeline_processed Indexes** (2 total):
1. PRIMARY KEY (pipeline_id, space_id, wal_pos) — composite btree
2. (processed_at) — btree (cleanup job for old offsets)
