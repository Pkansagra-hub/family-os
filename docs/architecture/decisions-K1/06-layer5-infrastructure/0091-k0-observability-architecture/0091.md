# ADR-0091: K0 Observability Architecture

**Status**: Proposed  \
**Date**: 2025-10-31  \
**Authors**: @observability-wg  \
**Parents**: ADR-0001 (K0/K1 Kernel Split), ADR-0044 (K0 Bridge HTTP/2 + FlatBuffers)  \
**Related**: ADR-0029 (Prometheus RED Method), ADR-0030 (Intelligent Trace Sampling), ADR-0038 (Audit Trail to K0 Receipts), ADR-0089 (K0 Bridge Policy Enforcement)

---

## Context

K0 kernel currently exposes `/obs.emit` for telemetry ingestion and provides a Prometheus-backed `MetricsExporter` stub, but comprehensive observability is incomplete.

- **Signal gaps**: Pipelines (P01–P20), storage primitives, policy enforcement, and bridge flows lack standardized metrics, spans, and structured logs. Existing dashboards (deploy/generated) cover a subset of components and are not versioned.
- **Trace propagation**: `cognitive_trace_id` attachment is inconsistent across K0 ingress (HTTP ports), UnitOfWork, bus dispatcher, outbox, and SSE. Without deterministic propagation, dashboards cannot correlate events end-to-end.
- **Privacy & compliance**: Observability signals must respect privacy bands (GREEN/AMBER/RED/BLACK) and obligations (mask/redact). Current emitters do not enforce policy-aligned redaction before persistence.
- **Edge-only constraint**: FamilyOS forbids cloud telemetry. Observability stack must run on-device (Prometheus TSDB, Tempo/OTLP receiver, Loki-equivalent for logs) with bounded resource usage.
- **Operational readiness**: Without consistent metrics and traces, QoS violations, WAL lag, and policy failures can go undetected. Gate 5 requires documentation and dashboards for every change; lack of ADR blocks downstream implementation (Gate 3).

This ADR establishes architecture, signal taxonomy, storage choices, and governance necessary to complete Milestone M1 → Epic E1 Issue E1.1.

---

## Decision

Adopt a unified observability architecture for K0 kernel with the following pillars.

1. **Signal Taxonomy**
   - **Metrics (Prometheus RED+USE)**: Standardize naming `k0.<component>.<metric>` with low-cardinality labels (for example `{pipeline="p01", privacy_band="amber"}`). Cover every pipeline (P01–P20), storage primitive, policy enforcement module, QoS scheduler, UnitOfWork, WAL, bus dispatcher, outbox, SSE, and observability ingress.
   - **Traces (OpenTelemetry)**: Define span hierarchy `k0.port` → `k0.minimal_gate` → `k0.pep` → `k0.uow` → `k0.pipeline.pXX.stage` → `k0.bus.dispatch`/`k0.outbox`/`k0.sse`. Mandatory attributes include `cognitive_trace_id`, `privacy_band`, `space`, `policy_version`, `unit_of_work_id`, and `wal_offset`. Sampling defaults to ADR-0030 (1 % baseline, error-tail 100 %).
   - **Logs (Structured JSON)**: Emit machine-parseable logs with `cognitive_trace_id`, `privacy_band`, `component`, `event`, `severity`, and `obligations_applied`. Logs are ingested locally (for example, Loki-compatible store) with retention aligned to privacy band policies.
   - **Observability Events**: `ObservabilityEmitter` publishes metric/log/trace updates to `ForwardedMetricsBuffer`, ensuring WAL-backed durability for offline analysis.

2. **On-Device Storage & Exposure**
   - **Prometheus TSDB**: Expose `/metrics` endpoint guarded by edge auth. Configure retention (default 15 days) and cardinality guardrails (<1,000 series per metric). Provide WAL snapshots for quick recovery.
   - **Tempo-compatible Trace Store**: Deploy local Tempo (or equivalent) receiving OTLP batches from K1 bridge via HTTP/2. Retention defaults 7 days hot with optional downsampling.
   - **Structured Log Store**: Maintain on-device log store with index by `cognitive_trace_id` and privacy band. Provide CLI queries and SSE notifications for high-severity events.

3. **Privacy & Policy Enforcement**
   - **Redaction Obligations**: Integrate with ADR-0089 policy enforcement module. Observability data must apply obligations before persistence (mask fields, remove payloads for RED/BLACK bands).
   - **Band-Aware Dashboards**: Dashboards must filter by privacy band and respect obligations (for example, show counts but not sensitive values for RED/BLACK).
   - **Auditability**: Emit receipt annotations capturing observability writes (ADR-0038) for compliance review.

4. **Governance & Workflow**
   - **5-Gate Compliance**: Gate 1 (this ADR) informs Gate 2 contracts (`metrics_payload.yml`, `trace_batch.yml`, `log_batch.yml`, `dashboard_catalog.yml`), Gate 3 implementation, Gate 4 test suites, Gate 5 documentation updates.
   - **Contracts-first**: Observability payload schemas live under `contracts/k0/observability/`. CI enforces schema adherence and version bumps.
   - **Dashboard Versioning**: Dashboards stored as JSON under `deploy/k0/observability_dashboards/` with semantic versioning and automated validation.
   - **Alerting Rules**: Define core alerts (QoS saturation, WAL lag, DLQ growth, policy violations) with on-device notification pipeline.
   - **Performance Budgets**: Observability operations must respect P95 budgets (metrics flush <120 ms, trace export <150 ms, log ingestion <100 ms). Monitoring for budget regressions is mandatory.

## Consequences

### Positive

- Comprehensive observability across all K0 components enables fast debugging and compliance audits.
- Aligns K0 with FamilyOS privacy mandates (band-aware dashboards, redaction obligations).
- Establishes reproducible workflow (contracts, dashboards, alerts) ensuring future changes respect the 5-Gate process.
- On-device stack maintains privacy-first posture; no cloud dependencies.

### Negative

- Increased resource usage (storage for metrics, traces, logs) requiring sizing and retention management.
- Additional development effort to instrument every pipeline, maintain contracts, and update dashboards.
- Trace sampling and log retention must be tuned to avoid device saturation.

### Risks & Mitigations

- **Cardinality explosion**: Mitigated via naming conventions, CI linting for label values, and runtime guards.
- **Performance overhead**: Mitigated by asynchronous exporters, batching, and budget regression tests.
- **Privacy leakage**: Mitigated by enforcing obligations before persistence and band-aware dashboards.
- **Operational drift**: Require quarterly review of dashboards and alerts, with Gate 5 memory updates.

---

## Alternatives Considered

### Alternative 1: Dashboard-Only Minimal Metrics

- **Why rejected**: Lacks traces/logs for forensic analysis; does not satisfy policy/receipt requirements; insufficient for edge debugging.

### Alternative 2: Cloud-Hosted Observability

- **Why rejected**: Violates FamilyOS edge-only mandate; introduces privacy and dependency risks.

### Alternative 3: Ad-hoc Instrumentation Per Pipeline

- **Why rejected**: Leads to inconsistent naming, missing contracts, and untestable dashboards; fails 5-Gate governance.

## Implementation Notes

- **Phase 1 (Milestone M1)**: Implement contracts, instrumentation for ingress (ports, Minimal Gate, PEP, UnitOfWork), `/obs.emit` hardening, and metrics exporter integration.
- **Phase 2 (Milestone M2)**: Extend instrumentation to pipelines P01–P10, storage primitives, bus dispatcher, SSE, outbox; deploy dashboards and alerts.
- **Phase 3 (Milestone M3)**: Complete coverage P11–P20, integrate with sync (P07) and policy obligations, finalize redaction ledger observability.
- **Testing**: Add integration suites validating metrics snapshot exposure, trace propagation, log ingestion; load tests verifying P95 budgets.
- **Rollback**: Feature-flag observability exporters; revert to minimal metrics if resource pressure detected.
