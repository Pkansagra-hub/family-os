# ADR-0002: Actor Model for Agent Isolation

**Status:** Accepted
**Date:** 2025-10-10
**Last Updated:** 2025-10-17 (M1 Context: See ADR-0072 for dynamic agent creation, ADR-0073 for lifecycle FSM enhancements)
**Deciders:** K1 Architecture Team
**Technical Story:** K1 Agent Fabric - Multi-Agent Coordination

---

## Context

K1 Intelligence Module must coordinate multiple LLM/SLM agents concurrently (1-3 agents per session, 10-15 sessions per device). Each agent has:

1. **Private State**: Persona, context window, working memory, KV cache
2. **Concurrent Execution**: Multiple agents process tasks simultaneously without blocking
3. **Fault Isolation**: One agent crash must not affect others or the kernel
4. **Communication**: Agents must coordinate (negotiate plans, share results, request clarification)
5. **Resource Limits**: Each agent has memory budget (64KB SessionState), CPU quota, token limits

**Current Situation:**

Traditional chatbot architectures use one of these patterns:
- **Shared State**: All agents read/write global state → race conditions, locks, deadlocks
- **Thread-Based**: One thread per agent → shared memory, no fault isolation, lock contention
- **Callback Hell**: Async callbacks with shared globals → spaghetti code, impossible to reason about

These approaches fail for multi-agent systems:
- ❌ **No isolation**: Agent crash = kernel crash
- ❌ **Concurrency bugs**: Race conditions, deadlocks, memory corruption
- ❌ **Unpredictable performance**: Lock contention blocks all agents
- ❌ **Testing nightmare**: Non-deterministic failures, hard to reproduce

**Constraints:**

- **Latency**: Agent message passing <0.5ms P95
- **Throughput**: Support 1-3 agents/session, 10-15 sessions concurrently
- **Memory**: Each agent limited to 64KB SessionState + KV cache
- **Fault Tolerance**: Agent failures must not crash kernel
- **Simplicity**: No locks, no shared memory, no mutexes

**Forces:**

- 📈 **Actor Model benefits**: Fault isolation, no locks, location transparency, supervision trees
- 📉 **Message passing overhead**: Copying messages vs shared memory
- 📈 **Proven at scale**: Erlang (WhatsApp 2M connections/server), Akka (Twitter, PayPal), Orleans (Microsoft Halo)
- 📉 **Learning curve**: Different mental model than threads
- 📈 **Deterministic testing**: Message passing = no race conditions

---

## Decision

We adopt the **Actor Model** (Hewitt, 1973) as the foundational concurrency paradigm for **ALL K1 components** (AI agents + pure actors).

### **Core Principles**

**APPLIES TO ALL K1 COMPONENTS:** These Actor Model principles govern ALL 52 K1 modules, whether AI agents (4 components) or pure actors (48 components).

**1. Actors are Isolated Entities**
- Each component is an **actor** with private state (no shared memory)
- Applies to: AI agents (Concierge, Planner, Researcher, Safety Watch) AND pure actors (Orchestrator, Supervisor, Router, SessionState, etc.)
- State modified only by processing messages from mailbox
- No direct access to other actors' state

**2. Message Passing is the Only Communication**
- ALL components communicate via **asynchronous messages** (mailbox queues)
- Messages are immutable (FlatBuffers serialization)
- No RPC, no shared state, no callbacks
- Applies equally to: AI agent ↔ AI agent, pure actor ↔ pure actor, AI agent ↔ pure actor

**3. Mailboxes Decouple Senders and Receivers**
- Each component has a **lock-free MPSC queue** (Multi-Producer Single-Consumer)
- Senders enqueue without blocking
- Receivers process messages in order (FIFO)
- ALL 52 K1 modules have mailboxes (no exceptions)

**4. Supervision Trees Isolate Failures**
- **Supervisor** (pure actor) monitors health of ALL components (1Hz pings)
- Component crash → supervisor detects, logs, notifies orchestrator
- Failed component removed from roster, resources reclaimed
- Other components continue unaffected
- Supervision applies equally to AI agents and pure actors

**5. Location Transparency (Future-Proof)**
- Components identified by `component_id` (UUID), not memory address
- Mailbox routing works locally or remote (future: distributed K1)
- Enables component migration, load balancing, clustering
- ALL components addressable by ID (AI agents, pure actors, infrastructure)

---

### **🤖 Agent Intelligence Layer: AI Agents = Actors + LLMs**

**CRITICAL CLARIFICATION:** K1 has TWO types of actors:

1. **AI Agents (4 components):** Actors + LLM integration
2. **Pure Actors (48 components):** Actors only (no LLMs)

**Both use Actor Model (above principles), but ONLY AI agents call LLMs for reasoning.**

#### **AI Agents: Actors + LLM Integration**

**AI agents combine TWO paradigms:**

**1. Actor Model (Hewitt 1973) — For Concurrency & Fault Isolation**
- Private state, mailboxes, supervision trees (SAME as pure actors)
- Message-passing between components (no shared memory)
- Fault isolation (crash doesn't affect others)
- **Foundation**: All concurrency mechanisms from Actor Model

**2. LLM/SLM Integration — For Intelligence & Reasoning (ONLY AI agents)**
- Each AI agent has **persona prompts** stored in Model Hub (`k1/model_hub/prompt_library/agent_prompts/`)
- AI agents call **Model Hub** to invoke LLMs: `await model_hub.call(prompt, context)`
- Supported providers: **OpenAI** (GPT-4), **Anthropic** (Claude), **vLLM** (local GPU), **Ollama** (local CPU)
- AI agents use **LLM reasoning** to evaluate tasks, generate plans, make decisions
- **Intelligence Layer**: ONLY for AI agents, pure actors do NOT call Model Hub

**Key Principle:**
> **AI Agents = Actors + LLMs** — Actor Model (concurrency/isolation) + Model Hub (intelligence). Pure Actors = Actor Model only.

#### **The 4 AI Agents in K1**

1. **Concierge Agent** — Chat interface, NLU, intent classification
2. **Planner Agent** — Multi-step plan generation with reasoning
3. **Researcher Agent** — Information synthesis from multiple sources
4. **Safety Watch Agent** — Content filtering using ML models

**Example: Planner Agent (AI Agent) with LLM Reasoning**

```python
class PlannerAgent:
    """
    AI Agent that generates execution plans using LLM reasoning

    Architecture:
    - Actor: Isolated process with mailbox (Actor Model - ADR-0002)
    - Intelligence: Calls GPT-4/Claude via Model Hub for plan generation
    """

    def __init__(self, agent_id: str, model_hub: ModelHub, mailbox: AgentMailbox):
        self.agent_id = agent_id
        self.model_hub = model_hub
        self.mailbox = mailbox
        self.capabilities = ["planning", "task_decomposition", "tool_selection"]

    async def handle_task(self, task: TaskAnnouncement):
        """Process task using LLM reasoning"""

        # 1. Load agent persona prompt from Model Hub
        prompt_template = await self.model_hub.get_prompt(
            role="planner",
            template="plan_generation_v2.jinja2"
        )

        # 2. Build context from session state
        context = {
            "user_query": task.intent,
            "available_tools": self.capabilities,
            "budget_ms": task.latency_budget_ms,
            "privacy_band": task.privacy_band
        }

        # 3. Call LLM via Model Hub (AI reasoning)
        model_response = await self.model_hub.call(
            prompt=prompt_template.render(context),
            model="gpt-4",  # or "claude-3-sonnet", "llama-3-8b"
            max_tokens=1500,
            temperature=0.7,
            trace_id=task.trace_id
        )

        # 4. Parse LLM response into structured plan (FlowDef)
        plan = self.parse_plan(model_response.content)

        # 5. Send proposal via mailbox (Actor Model)
        await self.mailbox.send(
            MailboxMessage(
                message_type="plan_proposal",
                payload={"plan": plan, "confidence": 0.9},
                trace_id=task.trace_id,
                sender_id=self.agent_id
            )
        )

        return plan

    def parse_plan(self, llm_output: str) -> FlowDef:
        """Parse LLM output into structured plan"""
        # Extract steps from LLM response
        steps = extract_steps(llm_output)
        return FlowDef(steps=steps, agent_id=self.agent_id)
```

**Contrast: Orchestrator (Pure Actor) WITHOUT LLM Reasoning**

```python
class Orchestrator:
    """
    Pure Actor that coordinates agents using deterministic logic

    Architecture:
    - Actor: Isolated process with mailbox (Actor Model - ADR-0002)
    - NO AI: Uses deterministic scoring, NO Model Hub calls
    """

    def __init__(self, component_id: str, mailbox: ComponentMailbox):
        self.component_id = component_id
        self.mailbox = mailbox
        self.agent_roster = []  # List of available agents
        # NO self.model_hub attribute (pure actors don't call LLMs)

    async def select_agent(self, task: TaskAnnouncement, proposals: List[Proposal]):
        """Select best agent using deterministic scoring (NO LLM call)"""

        # 1. Score proposals using deterministic rules
        def score_proposal(p: Proposal) -> float:
            score = 0.0
            # Rule 1: Prefer agents with matching capabilities
            if set(p.capabilities) & set(task.required_capabilities):
                score += 0.5
            # Rule 2: Prefer agents with lower latency
            score += (1.0 - min(p.latency_ms / 1000.0, 1.0)) * 0.3
            # Rule 3: Prefer agents with lower cost
            score += (1.0 - min(p.cost_usd / 0.01, 1.0)) * 0.2
            return score

        # 2. Select best proposal (NO LLM, pure Python)
        best_proposal = max(proposals, key=score_proposal)  # <1ms, deterministic

        # 3. Send approval via mailbox (Actor Model)
        await self.mailbox.send(
            MailboxMessage(
                message_type="plan_approval",
                payload={"approved_agent_id": best_proposal.agent_id},
                trace_id=task.trace_id,
                sender_id=self.component_id
            )
        )

        return best_proposal

    # NO parse_plan() method needed (no LLM output to parse)
    # NO model_hub integration (pure actor doesn't call LLMs)
```

**Key Differences:**

| Aspect | AI Agent (Planner) | Pure Actor (Orchestrator) |
|--------|-------------------|---------------------------|
| **LLM Calls** | ✅ Yes (via Model Hub) | ❌ No (deterministic only) |
| **Latency** | 50-150ms (LLM inference) | <1ms (CPU-bound) |
| **Cost** | $0.001/plan (GPT-4 tokens) | $0.00 (no API calls) |
| **Logic Type** | Non-deterministic (LLM varies) | Deterministic (rules) |
| **Persona** | Yes (`agent_prompts/planner.jinja2`) | No (config in YAML) |
| **Use Case** | Multi-step reasoning | Simple coordination |
| **Actor Model** | ✅ Yes (mailbox, isolation) | ✅ Yes (mailbox, isolation) |
| **Supervision** | ✅ Yes (Supervisor monitors) | ✅ Yes (Supervisor monitors) |

**Message Flow with LLM Integration:**

```
1. Orchestrator (Actor):
   send(planner_mailbox, TaskAnnouncement{...})
   → Enqueue to planner mailbox (Actor Model)

2. Planner Agent (Actor + AI):
   msg = mailbox.receive()  # Actor Model: Dequeue message

   → Load prompt: model_hub.get_prompt("planner", "plan_generation")
   → Call LLM: model_hub.call(prompt, model="gpt-4")  # AI: LLM reasoning
   → Parse response: plan = parse_plan(llm_output)

   → send(orchestrator_mailbox, PlanProposal{plan})  # Actor Model: Send result

3. Orchestrator (Actor):
   msg = mailbox.receive()  # Actor Model: Dequeue proposal
   → Score proposal (CPU-bound, no LLM)
   → send(planner_mailbox, PlanApproval{...})

4. Planner Agent (Actor):
   msg = mailbox.receive()  # Actor Model: Dequeue approval
   → Execute plan (may involve more LLM calls for sub-tasks)
```

**Model Hub Integration Points:**

| Component | Purpose | Latency |
|-----------|---------|---------|
| **Prompt Library** | Store agent persona prompts (Jinja2 templates) | 5-10ms (load) |
| **Model Router** | Route ModelCall to appropriate provider (OpenAI/Anthropic/vLLM/Ollama) | <1ms |
| **Model Adapters** | Call LLM APIs (GPT-4, Claude, Llama-3) | 100-500ms (LLM inference) |
| **Safety Filter** | 3-tier validation (Regex → ONNX → LLM) | 1-50ms |
| **KV Cache** | Share context across turns (avoid re-encoding) | 20-30ms (init) |

**Key Architectural Points:**

1. **Actor Model = Concurrency**: Mailboxes, supervision, fault isolation
2. **Model Hub = Intelligence**: LLM calls, prompt templates, safety filtering
3. **Agents call Model Hub frequently**: Every decision requires LLM reasoning
4. **Not just RPC**: Agents maintain state, have personas, learn from feedback
5. **See ADR-0049** for comprehensive prompt engineering and Model Hub integration details

#### **Cost Analysis: Hybrid vs All-AI Architecture**

**Production Workload (Typical Day):**
- 100 user turns → 100 Concierge calls (NLU)
- 50 planning tasks → 50 Planner calls (LLM reasoning)
- 20 research queries → 20 Researcher calls (synthesis)
- 200 content checks → 200 Safety Watch calls (ML)
- 1000 orchestration operations → Orchestrator (pure actor)
- 5000 health checks → Supervisor (pure actor)
- 10000 message routes → Router (pure actor)
- 2000 state updates → SessionState (pure actor)

**Hybrid Architecture (ACTUAL):**
```
AI Agent Costs:
  Concierge: 100 × $0.002 = $0.20
  Planner: 50 × $0.001 = $0.05
  Researcher: 20 × $0.005 = $0.10
  Safety Watch: 200 × $0.001 = $0.20
  Total AI: $0.55/day

Pure Actor Costs: $0.00/day
TOTAL: $0.55/day
```

**If All Components Were AI Agents (HYPOTHETICAL):**
```
All Operations via LLM:
  1000 orchestration × $0.001 = $1.00
  5000 health checks × $0.0002 = $1.00
  10000 routes × $0.0001 = $1.00
  2000 state updates × $0.0003 = $0.60
  + AI agent costs = $0.55
  TOTAL: $4.15/day (7.5× more expensive!)
```

**Latency Comparison:**
- **Hybrid**: 10% AI operations (100ms avg) + 90% pure actors (1ms avg) = **11ms average**
- **All-AI**: 100% LLM operations (100ms avg) = **100ms average** (9× slower!)

**Conclusion:** Hybrid architecture saves $3.60/day per user (~$1,300/year) and reduces average latency 9×.

#### **Design Principles**

**✅ Use AI Agents When:**
1. Natural language understanding required
2. Multi-step reasoning adds value over rules
3. Personalization through prompt engineering
4. Decision requires understanding of context/semantics
5. Acceptable latency: 50-500ms
6. Cost justified: $0.001-0.005 per operation

**✅ Use Pure Actors When:**
1. Deterministic logic sufficient (rules, scoring, selection)
2. Low latency critical: <5ms required
3. High frequency operations: 1000+/day
4. Coordination/routing/monitoring tasks
5. No natural language processing needed
6. Zero cost operations preferred

**❌ Anti-Patterns (DO NOT DO THIS):**

```python
# ❌ WRONG: Orchestrator as AI agent
class Orchestrator:
    async def select_agent(self, proposals):
        # Waste: LLM call for simple max() operation
        prompt = f"Choose best plan: {proposals}"
        response = await model_hub.call(prompt, model="gpt-4")
        return parse_selection(response)  # 100ms + $0.001 wasted!

# ✅ RIGHT: Orchestrator as pure actor
class Orchestrator:
    async def select_agent(self, proposals):
        # Efficient: Deterministic scoring
        return max(proposals, key=lambda p: p.score)  # <1ms, $0.00
```

```python
# ❌ WRONG: Router with AI reasoning
class Router:
    async def route(self, message):
        # Waste: LLM to determine routing (agent_id is in message!)
        prompt = f"Route message {message} to correct agent"
        destination = await model_hub.call(prompt)
        return parse_destination(destination)  # 100ms + $0.001 wasted!

# ✅ RIGHT: Router as pure actor
class Router:
    async def route(self, message):
        # Efficient: Direct mailbox lookup
        return self.mailboxes[message.receiver_id]  # <1μs, $0.00
```

**Mailbox Watermarks:**
- **High watermark** (50 messages): Block sender (slow consumer protection)
- **Low watermark** (25 messages): Resume sending

**Overflow Actions:**
- **Drop oldest messages** (for non-critical streams)

### **Actor Scheduling & Fairness**

**Committee Requirement:** Define how priority levels (0-3) map to CPU time and prevent starvation.

**Scheduling Algorithm: Weighted Fair Queueing (WFQ)**

| Priority Class | Weight | Min CPU Share | Max Starvation Time | Aging Rate |
|----------------|--------|---------------|---------------------|------------|
| URGENT (0) | 50% | 50% | N/A (never starves) | N/A |
| REALTIME (1) | 30% | 30% | 500ms | +1 priority/500ms |
| INTERACTIVE (2) | 15% | 15% | 1000ms | +1 priority/1s |
| BACKGROUND (3) | 5% | 5% | 5000ms | +1 priority/5s |

**Starvation Prevention:**
- **Aging**: Background tasks promoted to INTERACTIVE after 5s wait, then REALTIME after 6s total wait
- **Min Shares**: Each priority class guaranteed minimum CPU share (enforced via round-robin with class weights)
- **Fairness Guarantee**: No priority class starves >5s (provable via WFQ theorem)
- **Per-Class Quotas**: URGENT gets 50% of event loop time, REALTIME 30%, INTERACTIVE 15%, BACKGROUND 5%

**Implementation:**
```python
class PriorityScheduler:
    """WFQ scheduler with aging to prevent starvation"""

    def __init__(self):
        self.queues = {
            0: deque(),  # URGENT (50%)
            1: deque(),  # REALTIME (30%)
            2: deque(),  # INTERACTIVE (15%)
            3: deque(),  # BACKGROUND (5%)
        }
        self.weights = {0: 50, 1: 30, 2: 15, 3: 5}
        self.aging_thresholds = {1: 500, 2: 1000, 3: 5000}  # ms

    async def schedule_next(self) -> Message:
        """Select next message using WFQ with aging"""
        # Age messages (promote if waiting too long)
        self._age_messages()

        # Select based on weighted round-robin
        priority = self._select_priority_class()
        return self.queues[priority].popleft()

    def _age_messages(self):
        """Promote messages waiting > threshold"""
        now = time.time_ns() // 1_000_000  # ms
        for priority in [3, 2, 1]:  # BACKGROUND → INTERACTIVE → REALTIME
            threshold = self.aging_thresholds[priority]
            for msg in list(self.queues[priority]):
                wait_time = now - msg.enqueue_time
                if wait_time > threshold:
                    self.queues[priority].remove(msg)
                    self.queues[priority - 1].append(msg)  # Promote
```

**Metrics:**
- `actor_message_aged_total{from_priority, to_priority}`: Count of aged messages
- `actor_priority_wait_time_ms{priority}`: Histogram of wait time per priority

### **Router Security & Admission Control**

**Committee Requirement:** Define per-sender rate limits and DoS protection.

**Per-Sender Rate Limits (Token Bucket):**
- **Rate**: 100 tokens/second per sender
- **Burst**: 150 tokens (allow short bursts)
- **Max In-Flight Messages**: 200 messages per sender (hard limit)
- **Max In-Flight Bytes**: 1MB per sender (prevent memory exhaustion)

**Global Session Limits:**
- **Max Messages/Session**: 500 msg/s per session (all agents combined)
- **Max Memory/Session**: 10MB in-flight memory budget
- **Backpressure Cascade**: Session exceeds limits → reject new sends with `ADMISSION_DENIED`

**Rejection Semantics:**
```python
class AdmissionError:
    """Returned when admission control rejects message"""
    reason: str  # SENDER_RATE_LIMIT | SESSION_QUOTA | MAILBOX_FULL | AUTHN_FAILED
    retry_after_ms: int  # Exponential backoff suggestion
    current_limit: int  # Current limit value
    current_usage: int  # Current usage
```

**Capability Checking:**
- **Router validates** `lease_id` signature before enqueue (prevent unauthenticated sends)
- **Authn Tag**: Message envelope includes signed `lease_id` (HMAC-SHA256 verified)
- **Reject Unauthenticated**: Messages without valid `lease_id` → `AUTHN_FAILED` error

**Implementation:**
```python
class MessageRouter:
    """Router with admission control and capability checking"""

    def __init__(self, capability_manager):
        self.capability_manager = capability_manager
        self.token_buckets = {}  # sender_id → TokenBucket
        self.in_flight_messages = defaultdict(int)  # sender_id → count
        self.in_flight_bytes = defaultdict(int)  # sender_id → bytes

    async def send(
        self,
        message: Message,
        sender_capability: Capability
    ) -> Result[None, AdmissionError]:
        """Send message with admission control"""

        # 1. Verify capability
        if not self.capability_manager.verify(sender_capability):
            return Err(AdmissionError(
                reason="AUTHN_FAILED",
                retry_after_ms=0
            ))

        # 2. Check sender rate limit
        bucket = self.token_buckets.get(message.sender_id)
        if not bucket.consume(1):
            return Err(AdmissionError(
                reason="SENDER_RATE_LIMIT",
                retry_after_ms=bucket.refill_time_ms,
                current_limit=100,
                current_usage=bucket.tokens_used
            ))

        # 3. Check in-flight limits
        if self.in_flight_messages[message.sender_id] >= 200:
            return Err(AdmissionError(
                reason="SENDER_INFLIGHT_LIMIT",
                retry_after_ms=100
            ))

        # 4. Check memory budget
        msg_size = len(message.payload)
        if self.in_flight_bytes[message.sender_id] + msg_size > 1_000_000:
            return Err(AdmissionError(
                reason="SENDER_MEMORY_LIMIT",
                retry_after_ms=100
            ))

        # 5. Enqueue message
        await self._route_to_mailbox(message)

        # 6. Track in-flight
        self.in_flight_messages[message.sender_id] += 1
        self.in_flight_bytes[message.sender_id] += msg_size

        return Ok(None)
```

**Metrics:**
- `router_admissions_rejected_total{reason}`: Count of rejections by reason
- `router_token_bucket_exhausted_total{sender_id}`: Rate limit violations
- `router_inflight_messages{sender_id}`: Current in-flight message count
- `router_inflight_bytes{sender_id}`: Current in-flight byte count

## Alternatives Considered

### **Alternative 1: Thread-Based Concurrency**
One OS thread per agent, shared memory with locks.

**Pros:**
- ✅ Familiar model (most devs know threads)
- ✅ No message copying (shared pointers)
- ✅ Lower latency (no serialization)

**Cons:**
- ❌ **No fault isolation**: Thread crash = process crash
- ❌ **Concurrency bugs**: Race conditions, deadlocks, priority inversion
- ❌ **Unpredictable performance**: Lock contention blocks all threads
- ❌ **Testing nightmare**: Non-deterministic failures (Heisenbugs)
- ❌ **No location transparency**: Threads can't migrate across processes

**Why Rejected:**
Violates core principle of fault isolation. One agent bug crashes entire kernel. Industry experience (Erlang, Akka) demonstrates Actor Model superiority for fault-tolerant systems.

---

### **Alternative 2: Async/Await with Shared State**
Python async/await with global state dicts.

**Pros:**
- ✅ Lightweight (no threads)
- ✅ No GIL contention
- ✅ Easy to write (async/await syntax)

**Cons:**
- ❌ **Shared state**: All coroutines access same dict → race conditions
- ❌ **No isolation**: One coroutine error corrupts global state
- ❌ **Lock hell**: Must use locks/semaphores for safety
- ❌ **Testing complexity**: Non-deterministic behavior

**Why Rejected:**
Async/await is concurrency model, not isolation model. Doesn't solve fault isolation or shared state problems.

---

### **Alternative 3: CSP (Communicating Sequential Processes)**
Go-style channels for agent communication.

**Pros:**
- ✅ Message passing (no shared state)
- ✅ Composable channels (select/merge)
- ✅ Proven in Go ecosystem

**Cons:**
- ❌ **No supervision**: No built-in crash detection
- ❌ **Blocking sends**: Sender blocks if channel full
- ❌ **No location transparency**: Channels are local to process
- ❌ **Less mature in Python**: No standard library support

**Why Rejected:**
CSP excellent for coordination, but lacks Actor Model's supervision trees and location transparency. Actor Model more proven for fault-tolerant multi-agent systems (Erlang OTP).

---

### **Alternative 4: Microservices (Agent per Container)**
Each agent runs in separate Docker container, communicate via HTTP/gRPC.

**Pros:**
- ✅ Ultimate isolation (process + network)
- ✅ Independent scaling per agent
- ✅ Language-agnostic

**Cons:**
- ❌ **Latency**: HTTP/gRPC adds 10-100ms per call
- ❌ **Overhead**: Docker container = 20-50MB memory per agent
- ❌ **Complexity**: Service discovery, health checks, deployment
- ❌ **Overkill**: For 1-3 agents/session, too heavyweight

**Why Rejected:**
Violates latency budget (message passing <0.5ms). Microservices designed for distributed systems with separate teams, not single-machine multi-agent coordination.

## Performance & Backpressure (Canonical Flow)

**Agent Count (Canonical):** K1 has **58 agents total** = **4 AI agents** (Concierge, Planner, Researcher, Safety Watch) + **54 pure agents** (Orchestrator, Supervisor, Router, Protocol Monitor, Tool Runner, SessionState, etc.). All use Actor Model with mailboxes.

**Backpressure Path (End-to-End):**

```
Sender Agent
    ↓
Router Admission Control (5 checks in 0002c)
    ├─ Check 1: Capability Verification (HMAC-SHA256 lease)
    ├─ Check 2: Role Attestation (RBAC message types)
    ├─ Check 3: Token Bucket Rate Limit (100/s sustained, 150 burst)
    ├─ Check 4: In-Flight Limits (200 msgs, 1MB per sender)
    └─ Check 5: Session Limits (500 msg/s, 10MB per session)
    ↓
On REJECT: Return error code with retry hint
    • SENDER_RATE_LIMIT → backoff and retry
    • SESSION_QUOTA:INFLIGHT_* → wait for drain
    • MAILBOX_FULL → receiver applies overflow policy
    • AUTHN_FAILED:* → fix auth (no retry)
    ↓
On ADMIT: Enqueue to receiver mailbox
    ↓
Mailbox Watermarks (0002a)
    • HIGH watermark: 50 messages (backpressure activated)
    • LOW watermark: 25 messages (backpressure cleared)
    ↓
Overflow Policy (if >50 messages)
    • DROP_OLDEST: Drop oldest BACKGROUND message → DLQ
    • BLOCK_SENDER: Block until <25 messages
    • ALERT_SUPERVISOR: Log warning, emit metric
    ↓
Dead Letter Queue (DLQ)
    • Stores dropped messages (reason: OVERFLOW | TTL_EXPIRED | MAILBOX_FULL)
    • Capacity: 100 messages (FIFO, oldest dropped)
    • Retention: 5 minutes
    • Accessible via observability API
    ↓
Alerting (0002d)
    • MailboxDepthHigh: depth > 40 for 2 min
    • DLQFull: DLQ size > 90 for 1 min
    • TTLExpiredHigh: TTL expirations > 5/5min
```

**Message TTL (Time-To-Live):** All messages have **default TTL = 30s** (configurable per-message). Expired messages moved to DLQ with `reason="TTL_EXPIRED"` before processing.

**Trace Propagation (MUST):** All messages carry `cognitive_trace_id` end-to-end (sender → router.admission → mailbox.enqueue → actor.recv → mailbox.dequeue). This ID **MUST** be preserved in:
- All structured logs (JSON format)
- All OpenTelemetry spans
- DLQ entries (for debugging expired/dropped messages)
- Prometheus metric labels (where applicable)

**Operators:** Use Grafana dashboards (0002d) to trace: router rejections → mailbox watermarks → DLQ entries → alerts. All thresholds mirror policy limits for visual clarity.

### **Testing Strategy**

**Unit Tests:**
- MPSC queue correctness (enqueue/dequeue)
- Backpressure watermarks (high/low)
- Supervisor health checks (ping/timeout)

**Integration Tests:**
- Multi-agent message flows (orchestrator → planner → executor)
- Agent crash recovery (supervisor cleanup)
- Mailbox overflow (backpressure actions)

**Fault Injection:**
- Kill agent mid-message processing
- Fill mailbox to trigger overflow
- Supervisor timeout (agent hangs)

**Performance Tests:**
- Message latency benchmarks (P50/P95/P99)
- Throughput tests (messages/sec)
- Concurrency tests (10-15 sessions)

### **Rollback Plan**

**If Actor Model Fails:**

**Criteria for Rollback:**
- Message latency >2ms P95 (4x budget exceeded)
- Supervisor overhead >5% CPU (5x budget exceeded)
- Team velocity <50% of thread-based (too difficult)

**Rollback Steps:**
1. Replace mailboxes with direct function calls
2. Use async/await with shared state (locks)
3. Remove supervisor (rely on try/except)
4. Update tests (remove message mocking)

**Rollback Cost:** ~4 weeks (re-architect + test)

**Rollback Trigger:** Decision by architecture team after 2 months of development
