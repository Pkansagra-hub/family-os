# ADR-0095: Shared vs Per-Session Resource Map

**Status:** Accepted
**Date:** 2026-04-11
**Deciders:** K1 Architecture Team
**Technical Story:** Issue 2.0.10 — MS-2 Pre-Requisite. Resolves audit findings B-BUS-2, W-FAB-2, B-FAB-2, W-SS-2, B-BUS-4.

---

## Context

### Problem Statement

The K1 kernel bootstrap (`k1/kernel/bootstrap.py`) creates **ONE of everything** — a single Bus, single SSM, single Fabric, single FSM — hard-wired for a single session. Moving to multi-session support (MS-2 Epic 2.1: `KernelService`) requires an explicit decision about which components are **shared across all sessions** (Tier 1) and which are **created per-session** (Tier 2).

No such decision exists in the codebase today. Multiple audit findings are blocked waiting for this:

| Audit ID | Severity | What's Blocked |
|----------|----------|----------------|
| **B-BUS-2** | HIGH | Shared vs per-session Bus topology undecided |
| **W-FAB-2** | HIGH | `SessionStateReaderAdapter(manager, session_id)` is per-session — Fabric must be too |
| **B-FAB-2** | HIGH | No `create_shared()` factory method for Orchestrator/Planner Fabric |
| **W-SS-2** | HIGH | `DeltaBusAdapter` needs Bus ref — circular bootstrap risk if ordering is wrong |
| **B-BUS-4** | HIGH | `IMailboxRouter` register/unregister has no lifecycle hooks for multi-session |

### Current Situation

`start_kernel()` in `k1/kernel/bootstrap.py` (post-2.0.9, 29-field `KernelRuntime`) creates a flat, single-session component graph:

```
start_kernel()
  ├── BusFactory.create_local_ordered()          → bus
  ├── BusFactory.create_mailbox_router()          → router
  ├── router.register("front_half")               → front_mailbox
  ├── router.register("back_half")                → back_mailbox
  ├── _create_model()                             → model
  ├── _create_session_state()                     → session_state
  ├── _create_capability_registry()               → capability_registry
  ├── _create_fabric()                            → fabric_instance
  ├── ConciergeController(bus, router)            → fsm
  ├── 9 FSM late-wired setters
  ├── ToolContext (front + back)                  → front_ctx, back_ctx
  ├── ToolDispatcher (front + back)               → front_dispatcher, back_dispatcher
  ├── ExperienceLayer, DeltaAggregator, HILCoordinator, Weave*, DeadLetter
  ├── OrchestratorStub                            → orchestrator
  └── KernelRuntime(29 fields)
```

**Everything shares ONE bus, ONE SSM, ONE set of mailboxes.** There is zero session_id awareness, zero component sharing strategy, and zero lifecycle management for multi-session teardown.

### Constraints

1. **Existing 43 bus topic constants are bare strings** (e.g., `k1.user.input.v1`) — no session_id prefix. Changing them would touch 28 publishers and 25 subscribers.
2. **Bus is 100% synchronous** (`threading.Lock/RLock`). Async callers use `AsyncBusBridge` (Issue 2.0.1).
3. **SessionStateManager uses `threading.RLock`** for writes — per-session isolation required to prevent cross-session lock contention.
4. **Orchestrator needs cross-session dispatch** — a HIGH-tier task from Session A may involve shared Planner/Fabric resources.
5. **155 existing tests pass** and must continue to pass (single-session backward compatibility).

### Forces at Play

- 📈 **Session isolation**: Per-session Bus prevents Session A's delta events from reaching Session B's aggregator
- 📉 **Memory overhead**: Per-session Bus + TimingChain + middleware stack per session
- 📈 **Bare topic compatibility**: Per-session Bus avoids rewriting 43 topic constants
- 📉 **Cross-session coordination**: Shared components (Orchestrator) need a separate communication path
- 📈 **Clean lifecycle**: Per-session Bus can be `.close()`d on session destroy — no leaked subscriptions
- 📈 **Proven factories**: All 6 component factories already accept injected ports — no DI refactoring needed

---

## Decision

### Chosen Approach: Two-Tier Bootstrap with Per-Session Bus

We adopt a **two-tier bootstrap architecture** where components are explicitly classified as **Tier 1 (shared, created once at startup)** or **Tier 2 (per-session, created in `create_session()`)**.

**Bus topology: Per-session Bus** (resolves B-BUS-2).

Each session gets its own isolated `LocalBus` instance. A separate lightweight `system_bus` handles admin/health events that span sessions (Orchestrator dispatch, Planner notifications, health checks).

### Tier 1 — Shared Components (created once in `KernelService.startup()`)

| Component | Why Shared | Key Constraint |
|-----------|-----------|----------------|
| **system_bus** | Cross-session Orchestrator dispatch, admin health events | Lightweight, no TimingChain, no session state |
| **ModelHub** | Stateless LLM gateway, thread-safe, expensive to initialize | Single instance serves all sessions via `execute(HubRequest)` |
| **Shared Fabric** | Orchestrator/Planner need capability execution without session context | Uses `NullSessionStateReaderAdapter` (B-FAB-2 → Issue 2.0.13) |
| **Orchestrator** | Task dispatch is cross-session; `session_id` passed per-request in `TaskEnvelope` | Receives `session_id` in envelope metadata, routes to correct session |
| **Planner** | Planning engine is stateless per-plan; `session_id` bound per `PlanRequest.context` | `SnapshotStateReadAdapter` pre-bound per pipeline run |
| **Bridge** | Single K0 connection, connection pooling | `SinkBridgeClient` for offline; future `OnlineBridgeClient` shared |
| **CapabilityRegistry** | Static capability catalog, read-only after boot | Shared reference, no mutation |

**Tier 1 bootstrap order** (strict dependency chain):

```
S1. system_bus = BusFactory.create_local()           # lightweight, no ordering
S2. model_hub  = ModelHubFactory.create_standalone()  # stateless LLM gateway
S3. bridge     = SinkBridgeClient()                   # offline mode (or OnlineBridgeClient)
S4. shared_fabric = FabricFactory.create_shared(      # NEW method from Issue 2.0.13
        bus=system_bus,
        model_hub=model_hub,
        bridge=bridge,
    )                                                 # NullSessionStateReaderAdapter internally
S5. orchestrator = OrchestratorFactory.create_production(
        fabric=shared_fabric,
        bus=system_bus,
        planner=MockPlannerAdapter(),                 # stub, hot-swapped at S6b
        ...
    )
S6. planner = PlannerFactory.create_production(
        fabric=shared_fabric,
        bus=system_bus,
        ...
    )
S6b. orchestrator._planner_port = PlannerAdapter(planner)  # cross-wire
```

### Tier 2 — Per-Session Components (created in `KernelService.create_session(device_id)`)

| Component | Why Per-Session | Key Constraint |
|-----------|----------------|----------------|
| **session_bus** | Total event isolation between sessions. 43 bare topic constants work unchanged. | `BusFactory.create_local_ordered()` with TimingChain |
| **SSM** | Per-session state manager with `threading.RLock` for writes | Created AFTER session_bus (resolves W-SS-2 ordering) |
| **Per-session Fabric** | Needs `SessionStateReaderAdapter(ssm, session_id)` bound to ONE session | Resolves W-FAB-2 — each session gets fresh adapter |
| **ConciergeController/FSM** | FSM state machine is per-session (one conversation per session) | 9 late-wired setters, only `set_session_state()` required |
| **Tool dispatchers + ToolContext** | `cognitive_trace_id` is per-turn, `session_manager` is per-session | front_ctx + back_ctx created with session-scoped refs |
| **ExperienceLayer** | Zero-param constructor, pure algorithm, reads from session FSM state | One per session |
| **DeltaAggregator/Applicator** | Closures over session-scoped SSM and session_bus | Flush writes to per-session bus |
| **HiTL Coordinator** | Callbacks emit to per-session bus | One per session |
| **Mailboxes** | `front_{session_id}`, `back_{session_id}` on per-session router | Namespaced actor IDs for clarity |
| **WeaveBatcher, WeavePolicy, ActivityTracker** | Per-session adaptive delivery state | Track per-session user patterns |
| **DeadLetterConsumer** | Subscribes to per-session bus dead-letter topic | Created LAST (subscribes immediately in `__init__`) |
| **Ledger** | Per-session audit trail | `LedgerWriter(store, session_id)` |

**Tier 2 bootstrap order** (strict dependency chain, resolves W-SS-2):

```
P1. session_bus    = BusFactory.create_local_ordered()      # per-session, with TimingChain
P2. session_router = BusFactory.create_mailbox_router()
P3. front_mailbox  = session_router.register(f"front_{session_id}")
P4. back_mailbox   = session_router.register(f"back_{session_id}")
P5. ssm = SessionStateFactory.create_with_ports(            # Bus exists → no circular dep
        storage=SQLiteStorageAdapter(db_path),
        events=SessionBusAdapter(session_bus),               # session_bus ref safe here
        ...
    )
P6. session_fabric = FabricFactory.create_with_ports(
        state_reader=SessionStateReaderAdapter(ssm, session_id),  # TWO args (W-FAB-2)
        event_port=FabricBusAdapter(session_bus),
        delta_bus=FabricBusAdapter(session_bus),                  # SAME instance, dual-role
        ...
    )
P7. fsm = ConciergeController(bus=session_bus, router=session_router)
P8. fsm.set_session_state(ssm)                               # REQUIRED setter
P9. [remaining FSM setters, ToolContexts, dispatchers, experience, delta, hitl, weave]
P10. dead_letter = DeadLetterConsumer(bus=session_bus)        # LAST — subscribes in __init__
P11. consumer_task = asyncio.create_task(_mailbox_consumer(runtime))
```

### Bus Architecture: Per-Session Bus + System Bus

```
KernelService
├── system_bus (admin/health, cross-session Orchestrator dispatch)
│   ├── Orchestrator subscriptions
│   ├── Planner subscriptions
│   └── Health/admin topics
│
└── sessions: dict[session_id, SessionInstance]
     └── SessionInstance
          ├── session_bus (isolated LocalBus per session)
          │   ├── FSM 20 topic subscriptions
          │   ├── Front event subscriptions (4 topics)
          │   ├── DeadLetterConsumer (1 topic)
          │   └── All 43 bare topic constants — UNCHANGED
          ├── session_router (MailboxRouter per session)
          │   ├── front_{session_id} mailbox
          │   └── back_{session_id} mailbox
          ├── ssm (per-session SessionStateManager)
          ├── session_fabric (per-session Fabric with real StateReader)
          ├── fsm (per-session ConciergeController)
          └── [dispatchers, experience, delta, hitl, weave, ledger]
```

**Cross-session communication path** (Orchestrator → session):

When Orchestrator needs to deliver a result to a specific session, it publishes to the `system_bus` with `session_id` in envelope metadata. `KernelService` maintains a routing table (`session_id → session_bus`) and bridges the envelope to the correct per-session bus.

```python
# KernelService routes Orchestrator results to correct session
system_bus.subscribe("k1.task.*", lambda env: self._route_to_session(env))

def _route_to_session(self, envelope: Envelope) -> None:
    sid = envelope.metadata.get("session_id")
    if sid and sid in self._sessions:
        self._sessions[sid].bus.publish(envelope)
```

### Circular Bootstrap Resolution (W-SS-2)

The `DeltaBusAdapter` (currently a stub) will need a bus reference when implemented. The strict ordering P1 → P5 ensures the session_bus exists before SSM construction:

```
P1: session_bus = BusFactory.create_local_ordered()     # Bus exists
         ↓
P5: ssm = SessionStateFactory.create_with_ports(
        events=SessionBusAdapter(session_bus),           # Safe — bus already created
        ...
    )
```

If `DeltaBusAdapter` requires two-phase binding (create SSM first, bind adapter later), the proven pattern from `SessionStateFactory.create_with_ports()` applies:

```python
ssm = SessionStateFactory.create_with_ports(writer=None, ...)
writer = DirectWriterAdapter(manager=ssm, guard=ssm.mutation_guard)
ssm._writer_port = writer  # two-phase bind
```

### MailboxRouter Lifecycle (B-BUS-4)

Per-session Bus **eliminates** the need for MailboxRouter lifecycle hooks on a shared router. Each session has its own `session_router`:

- **Session create**: `session_router = BusFactory.create_mailbox_router()` — fresh router
- **Session destroy**: `session_router.close()` — closes all mailboxes, GC-eligible

No shared router registration/deregistration needed. No lifecycle hooks required. B-BUS-4 is resolved by architecture, not code.

### Rationale

1. **43 bare topic constants unchanged** — Per-session Bus means `k1.user.input.v1` works as-is. No `k1.{session_id}.user.input.v1` refactoring across 28 publishers and 25 subscribers.

2. **Total session isolation** — Session A's `DeltaAggregator` flush never reaches Session B's bus. No topic collision possible by design.

3. **Clean session lifecycle** — `session_bus.close()` in `destroy_session()` prevents all further publishes. Router and mailboxes become GC-eligible immediately. No leaked subscriptions.

4. **Per-session TimingChain** — Each session has its own causal context. No cross-session dependency tracking. Correct for independent conversation flows.

5. **Lightweight cost** — `LocalBus` is ~500 bytes + middleware stack. At 100 max sessions, overhead is ~50KB total. Negligible.

6. **Backward compatible** — Single-session mode (current tests) is just "one session" in the new model. 155 existing tests unaffected.

## Alternatives Considered

### Alternative 1: Single Shared Bus with Topic Namespacing

**Description:** One `LocalBus` for all sessions. Topics prefixed with `session_id` (e.g., `k1.{session_id}.user.input.v1`). MailboxRouter namespaces actors.

**Pros:**

- Single bus instance — less memory
- Orchestrator publishes directly to correct session topic
- No routing bridge needed

**Cons:**

- **43 topic constants must be rewritten** to include `session_id` parameter — touches 28 publishers, 25 subscribers, all envelope builders
- **TopicTrie match complexity grows** with session count (all patterns share one trie)
- **No isolation guarantee** — subscriber bug could match wrong session's topics
- **Lifecycle complexity** — must track and unsubscribe all per-session handles on destroy
- **MailboxRouter lifecycle hooks needed** (B-BUS-4) — must add register/unregister events

**Rejected because:** Refactoring 43 topic constants across ~53 call sites is high-risk, high-effort, and gains nothing that per-session Bus doesn't provide more safely. The "Orchestrator needs cross-session dispatch" concern is solved more cleanly by a lightweight system_bus bridge.

### Alternative 2: Bus-Per-Component (Micro-Bus)

**Description:** Each component (Fabric, Orchestrator, etc.) gets its own bus. Events bridged between buses.

**Pros:**

- Maximum isolation
- Component-level fault containment

**Cons:**

- Explosion of bus instances (6+ per session)
- Complex event bridging graph
- Debugging nightmare — events span multiple buses
- No existing factory support

**Rejected because:** Over-engineered. Per-session Bus already provides sufficient isolation. Component boundaries are enforced by ports/adapters, not bus topology.

## Consequences

### Positive Consequences

- ✅ **Zero refactoring of existing bus topics** — all 43 bare topic constants work unchanged
- ✅ **Total session isolation** — per-session Bus prevents cross-session event leaks
- ✅ **Clean session lifecycle** — `session_bus.close()` is complete teardown, no leaked subscriptions
- ✅ **B-BUS-4 resolved by architecture** — per-session router eliminates need for lifecycle hooks
- ✅ **W-SS-2 resolved by ordering** — strict P1 → P5 ensures Bus exists before SSM
- ✅ **W-FAB-2 resolved by per-session Fabric** — fresh `SessionStateReaderAdapter(ssm, sid)` per session
- ✅ **B-FAB-2 unblocked** — shared Fabric uses `NullSessionStateReaderAdapter` via `create_shared()` (Issue 2.0.13)
- ✅ **155 existing tests unaffected** — single-session is "one session" in new model

### Negative Consequences

- ⚠️ **system_bus + routing bridge required** — KernelService must bridge Orchestrator results from system_bus to per-session bus (~20 LOC)
- ⚠️ **Memory overhead per session** — each session: LocalBus (~500B) + TimingChain + middleware + MailboxRouter + 2 mailboxes. Estimated ~5KB/session. At 100 sessions = ~500KB. Acceptable.
- ⚠️ **Two bus instances per session** — developers must be clear about when to use `session_bus` vs `system_bus`

### Risks & Mitigations

#### Risk 1: Orchestrator→Session routing adds latency

- **Likelihood:** Low
- **Impact:** Low
- **Mitigation:** Bridge is a synchronous `bus.publish()` call — microseconds. No network hop, no serialization.

#### Risk 2: Developers accidentally publish to wrong bus

- **Likelihood:** Medium
- **Impact:** Medium
- **Mitigation:** Per-session components receive only `session_bus` via DI. Only `KernelService` holds both bus references. Type annotations + code review.

#### Risk 3: system_bus subscription leaks on Orchestrator crash

- **Likelihood:** Low
- **Impact:** Low
- **Mitigation:** `KernelService.shutdown()` calls `system_bus.close()` which prevents further publishes. Orchestrator is shared (single instance), not per-session.

### Performance Impact

- **Per-session Bus creation:** ~0.1ms (LocalBus is lightweight)
- **Per-session memory:** ~5KB (Bus + Router + Mailboxes + TimingChain)
- **Cross-session routing:** ~0.01ms (synchronous publish, no serialization)
- **No impact on existing single-session performance** — identical code path

### Maintenance Impact

- **Clearer mental model** — "session owns its bus" is simpler than "shared bus with namespacing"
- **Easier debugging** — per-session bus capture isolates events to one session
- **Session teardown is trivial** — `bus.close()` + `router.close()` = done
