# ADR-0034: Adopt MCP as Default Tool Communication Protocol

**Status:** ✅ Approved
**Date:** 2025-10-13
**Decision Owner:** Platform Lead
**Authors:** K1 Architecture Team
**Category:** Integration & Protocols
**Related ADRs:** ADR-0033 (Three-Tier Sandboxing), ADR-0010 (Capability-Based Security), ADR-0032 (Egress Rules)

---

## Context

**Problem:** Without a standard protocol, each tool integration is bespoke (REST/gRPC/CLI wrappers), leading to adapter sprawl, inconsistent error models, and uneven isolation.

**Forces:**

1. **Standardization:** Need common protocol for tool discovery, invocation, and error handling
2. **Interoperability:** Tools should work across AI systems (Claude, Copilot, K1)
3. **Isolation:** Protocol must support process isolation (tools run outside K1 kernel)
4. **Vendor Neutrality:** Avoid lock-in to proprietary tool ecosystems

**Current State:**
- 100+ tools with unique interfaces (20 REST APIs, 30 CLI wrappers, 50 Python functions)
- Every tool requires custom K1 adapter code
- No standard error format (HTTP 500 vs JSON errors vs exit codes)
- Process isolation inconsistent (some in-process, some subprocess, some HTTP)

---

## Decision

**We adopt Model Context Protocol (MCP) as the default tool communication protocol for K1:**

### Core Principles

1. **MCP Client in K1:** K1 runs an MCP client that speaks spec version `2025-06-18` (pinned)
2. **MCP Servers in Sandboxes:** Tools expose MCP servers (stdio or HTTP) running inside sandbox tiers (ADR-0033)
3. **Standard Contract:** Use MCP's JSON Schema for parameters, structured errors, and timeouts
4. **Circuit Breaker Integration:** MCP client implements circuit breaker at protocol layer

### Protocol Details

**Transport:** JSON-RPC 2.0 over stdio (preferred) or HTTP
**Specification:** [modelcontextprotocol.io/specification/2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)
**Version Pinning:** Lock to spec version `2025-06-18`, migrate explicitly on updates

**Core Operations:**
- `initialize` — Handshake and capability negotiation
- `tools/list` — Discover available tools and their schemas
- `tools/call` — Invoke tool with validated parameters
- `shutdown` — Graceful termination

---

## Consequences

### Positive

1. **Reduced Adapter Code:** Single MCP client replaces 100+ custom adapters
2. **Cross-Ecosystem Compatibility:** Tools work with Claude, Copilot, and other MCP-compatible systems
3. **Consistent Error Handling:** JSON-RPC error codes (-32600 invalid request, -32601 method not found, -32603 internal error)
4. **Process Isolation:** stdio/HTTP transports naturally enforce separate processes
5. **Structured Validation:** JSON Schema for parameters enables client-side validation before tool execution

### Negative

1. **Protocol Churn:** MCP spec is evolving (2024 release), may require migrations
2. **Server Shims:** Legacy tools need MCP server wrappers (until native rewrites)
3. **Stdio Complexity:** Stdio transport requires process lifecycle management (spawn, IPC, cleanup)
4. **HTTP Overhead:** HTTP transport adds network latency for local tools (~10ms)

### Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Spec breaking changes | Pin version `2025-06-18`, test against spec examples before upgrade |
| Legacy tool compatibility | Provide MCP server template (Python/Rust), automated wrapper generator |
| Stdio process leaks | Implement robust cleanup (SIGTERM → 5s wait → SIGKILL) |
| Circuit breaker false positives | Tunable thresholds (5 failures, 10 min window, 60s cooldown) |

## Alternatives Considered

### Alternative 1: gRPC for All Tools

**Approach:** Define gRPC services for each tool, use Protobuf for schemas

**Pros:**
- Strong typing (Protobuf schemas compiled to code)
- Efficient binary protocol
- Streaming support (bidirectional RPC)

**Cons:**
- ❌ **Not a common lingua franca for LLM tools** — No major adoption in AI ecosystem
- ❌ **Heavier operationally** — Requires protobuf compilation, code generation, service definitions
- ❌ **Overkill for simple tools** — weather_api doesn't need streaming or binary encoding

**Verdict:** ❌ **Rejected** — MCP is lighter and emerging as AI industry standard

### Alternative 2: REST Per Tool

**Approach:** Each tool exposes REST API, K1 sends HTTP requests

**Pros:**
- Universal protocol (HTTP)
- Easy debugging (curl, Postman)
- No process management (tools run as services)

**Cons:**
- ❌ **Perpetuates inconsistency** — Every tool has different endpoints, error formats
- ❌ **No standard discovery** — How does K1 find tools? OpenAPI specs per tool?
- ❌ **Stateless overhead** — Each request requires auth, connection setup

**Verdict:** ❌ **Rejected** — Doesn't solve adapter sprawl or standardization problem

### Alternative 3: In-Process Function Calling Only

**Approach:** Tools as Python/Rust functions loaded in K1 process, OpenAI-style function calling

**Pros:**
- Zero IPC overhead
- Simple integration (just function calls)
- OpenAI compatibility

**Cons:**
- ❌ **Lacks process isolation** — Tool crash crashes K1 kernel (violates security principle)
- ❌ **No server-side validation** — All validation must happen in K1 (error-prone)
- ❌ **Not a protocol** — Function calling is LLM output format, not tool integration standard

**Verdict:** ❌ **Rejected** — Security risk (no isolation), not a true protocol

### Alternative 4: Custom K1 Protocol

**Approach:** Design proprietary K1 tool protocol

**Pros:**
- Full control over design
- Optimize for K1-specific needs

**Cons:**
- ❌ **Vendor lock-in** — Tools only work with K1, not portable to Claude/Copilot
- ❌ **Reinventing the wheel** — MCP already solves this problem
- ❌ **Ecosystem fragmentation** — K1 becomes isolated from broader AI tool ecosystem

**Verdict:** ❌ **Rejected** — MCP is open, vendor-neutral, and gaining adoption

## Acceptance Criteria

### MCP Client Implementation

```rust
// k1/mcp/client.rs
pub struct MCPClient {
    transport: MCPTransport,  // Stdio or HTTP
    spec_version: &'static str,  // "2025-06-18"
    timeout: Duration,
}

impl MCPClient {
    pub async fn initialize(&mut self) -> Result<InitializeResponse> {
        let request = json!({
            "jsonrpc": "2.0",
            "id": 1,
            "method": "initialize",
            "params": {
                "protocolVersion": self.spec_version,
                "capabilities": {}
            }
        });

        let response = self.send_request(request).await?;
        Ok(serde_json::from_value(response)?)
    }

    pub async fn list_tools(&mut self) -> Result<Vec<Tool>> {
        let request = json!({
            "jsonrpc": "2.0",
            "id": 2,
            "method": "tools/list",
            "params": {}
        });

        let response = self.send_request(request).await?;
        Ok(serde_json::from_value(response["tools"].clone())?)
    }

    pub async fn call_tool(&mut self, name: &str, arguments: Value) -> Result<Value> {
        let request = json!({
            "jsonrpc": "2.0",
            "id": 3,
            "method": "tools/call",
            "params": {
                "name": name,
                "arguments": arguments
            }
        });

        let response = tokio::time::timeout(
            self.timeout,
            self.send_request(request)
        ).await??;

        Ok(response)
    }
}
```

### Conformance Testing

Must pass:
1. **Spec compliance:** MCP client passes all examples from [modelcontextprotocol.io/examples](https://modelcontextprotocol.io/examples)
2. **Error handling:** Correctly handle JSON-RPC errors (-32600, -32601, -32603)
3. **Timeout enforcement:** Kill tool process if exceeds timeout
4. **Circuit breaker:** Open after 5 failures, cooldown 60s, test in HALF_OPEN

## Implementation Notes

### Stdio Transport (Preferred)

**Advantages:**
- No network ports required
- Natural process isolation
- Low latency (<1ms IPC)

**Implementation:**
```rust
let mut child = Command::new(&tool.server_path)
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped())
    .spawn()?;

let stdin = child.stdin.take().unwrap();
let stdout = BufReader::new(child.stdout.take().unwrap());

// Send JSON-RPC request to stdin
writeln!(stdin, "{}", serde_json::to_string(&request)?)?;

// Read JSON-RPC response from stdout
let mut line = String::new();
stdout.read_line(&mut line)?;
let response: JsonRpcResponse = serde_json::from_str(&line)?;
```

### HTTP Transport (For Remote Tools)

**Advantages:**
- Works with remote MCP servers
- Standard HTTP tools (curl, Postman)
- Connection pooling

**Implementation:**
```rust
let client = reqwest::Client::new();
let response = client.post(&tool.server_url)
    .json(&request)
    .timeout(Duration::from_millis(tool.timeout_ms))
    .send()
    .await?;

let json: JsonRpcResponse = response.json().await?;
```

### Circuit Breaker Integration

```rust
pub struct CircuitBreaker {
    failures: HashMap<String, Vec<Instant>>,
    failure_threshold: usize,  // 5
    time_window: Duration,      // 10 minutes
    cooldown: Duration,         // 60 seconds
}

impl CircuitBreaker {
    pub fn allow_request(&mut self, tool_name: &str) -> bool {
        let failures = self.failures.entry(tool_name.to_string()).or_default();

        // Remove failures outside time window
        failures.retain(|t| t.elapsed() < self.time_window);

        // Check if threshold exceeded
        failures.len() < self.failure_threshold
    }

    pub fn record_failure(&mut self, tool_name: &str) {
        self.failures.entry(tool_name.to_string())
            .or_default()
            .push(Instant::now());
    }
}
```

## Performance Targets

| Metric | Target | Notes |
|--------|--------|-------|
| MCP handshake | <50ms | initialize + tools/list |
| Stdio IPC | <1ms | JSON serialization + pipe write/read |
| HTTP round-trip | <10ms | Local HTTP POST to 127.0.0.1 |
| Timeout enforcement | 100% | Kill process if exceeds timeout |
| Circuit breaker | 5 failures → OPEN | 60s cooldown before retry |
